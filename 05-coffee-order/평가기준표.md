# 과제 5. 카페 주문 시스템 평가 기준표

> 평가자용 문서, v1.3 (2026-11-16)
> - 지원자 README의 도전 요구사항 4가지(다수 인스턴스, 동시성, 데이터 일관성, 테스트)를 기준으로 채점합니다.
> - 필수 API 4개와 README의 문제 해결 전략은 채점 전에 확인하는 전제 조건입니다. 지원자 README 4장에도 이 평가 방식을 안내했습니다.
> - 같은 폴더의 `solution/`(정답 서버)을 함께 사용합니다.

---

## 1. 배점 요약

| 영역 | 배점 | 판정 방법 |
|---|---|---|
| A. 다수 인스턴스 | 25 | 코드와 README를 읽고 판정. 가능하면 서버 2대를 띄워 확인 |
| B. 동시성 | 25 | 평가자가 동시 요청을 직접 보내 확인하고, 코드로 락 범위 판정 |
| C. 데이터 일관성 | 25 | 코드를 읽고 트랜잭션 경계와 외부 전송 위치를 판정 |
| D. 테스트 | 25 | 지원자 테스트 코드를 읽고 `./gradlew test`로 실행 |
| **합계** | **100** | |

- 이 과제는 API 명세를 지원자가 직접 정합니다. 요청을 보낼 때는 지원자 README의 API 명세를 따릅니다.

### 평가 순서

1. 2장의 전제 조건을 확인합니다.
2. 지원자 README에 적힌 방법으로 서버와 인프라를 실행합니다.
3. **B 영역에 쓸 사용자에게 포인트를 미리 충전합니다.** B1은 한 명에게 메뉴 하나의 3잔 값, B2는 다른 한 명(충전은 시나리오가 직접 함), B3는 서로 다른 50명에게 각각 1잔 값 이상을 충전해 둡니다. 충전 없이 보내면 전부 잔액 부족으로 실패합니다.
   - 사전 등록된 사용자만 허용하는 설계라면 제출 README의 초기 데이터에서 쓸 수 있는 ID를 찾습니다. 50명을 채울 수 없으면 **보낸 건수와 집계 증가분이 같은지**로 B3를 판정합니다.
   - **전제 조건(P3~P5)에서 쓴 사용자·메뉴와 겹치지 않게** 다른 ID를 씁니다. 같은 메뉴를 다시 써야 하면 직전 집계를 먼저 읽어 두고 **증가분**으로 판정합니다.
4. 3장 B 영역의 동시 요청 시나리오를 보냅니다.
5. 코드와 README를 읽고 A, C 영역을 판정합니다.
6. `./gradlew test`를 실행하고 D 영역을 판정합니다.
7. 5장의 치명 오류가 있는지 확인합니다.

> **동시 요청 보내는 방법**
> - 셸에서 `for i in $(seq 1 10); do curl -s -o /dev/null -w "%{http_code}\n" -X POST ... & done; wait`처럼 `&`를 붙여 요청을 동시에 보냅니다.
> - 응답 코드별 개수와 이후 잔액, 주문 수, 인기 메뉴 결과를 확인합니다.
> - 성공과 실패를 셀 때는 지원자 README가 정의한 응답 기준을 따릅니다. HTTP 상태 코드가 아니라 응답 본문의 상태 값으로 성공 여부를 표현하는 설계라면 본문 기준으로 셉니다. 어느 쪽이든 최종 잔액과 주문 수가 맞는지로 교차 확인합니다.
>
> **서버 2대로 확인하는 방법 (A 영역, 선택)**
> - 지원자 서버를 포트만 바꿔 두 번 실행합니다. (예: `SERVER_PORT=8081`처럼 지원자 README가 안내한 방법)
> - 위 동시 요청을 두 포트에 번갈아 보냅니다. 두 서버가 같은 DB와 저장소를 보지 않으면 이 단계는 건너뛰고 코드로만 판정합니다.
>
> **정답 서버와 비교하는 방법**
> - 판정이 애매하면 `solution/`을 실행하고 같은 시나리오를 보내 **한 가지 구현 예**를 확인합니다. 실행 방법은 `solution/README.md`에 있습니다.
> - **B 영역 판정을 먼저 끝내고, 지원자 서버와 컨테이너를 모두 내린 뒤에 정답 서버를 띄우세요.** 둘 다 8080·MySQL 3306·Redis 6379를 쓰므로, 겹쳐 실행하면 기동에 실패하거나 정답의 초기 데이터가 채점 중인 DB에 섞여 들어갑니다.
> - 정답 서버는 경로·응답 형식·에러 코드를 스스로 정한 구현이고, 지원자는 그것을 따를 의무가 없습니다(지원자 README 5장 「추가 조건」). **3장에 배점 항목이 없는 차이는 감점 사유가 아닙니다.**

## 2. 전제 조건

채점을 시작하기 전에 아래 항목을 확인합니다. 빠진 항목은 5장 치명 오류에 따라 처리합니다.

> P6(설계 문서) 네 항목 중 **문제 해결 전략·분석**이 없으면 F4, **ERD·API 명세서**가 없으면 F5입니다. 나머지 두 항목(**설계 의도**, **기술 선택 이유**)은 감점 항목이 아니라 A3·B4·C 영역의 설명 점수에서 자연히 반영되므로, 빠져 있으면 평가 의견에만 적고 따로 감점하지 않습니다.

| ID | 확인 항목 | 확인 방법 |
|---|---|---|
| P1 | 서버가 지원자 README의 안내대로 실행됨 | README의 실행 방법을 그대로 따라 함 |
| P2 | 메뉴 목록 조회 API가 메뉴 ID, 이름, 가격을 응답함 | 요청을 보내 확인 |
| P3 | 포인트 충전 API가 사용자 식별값과 충전 금액으로 충전함 (1원 = 1P) | 충전 후 잔액 확인. 응답에 잔액이 없으면 잔액 조회 수단이나 저장소를 직접 확인합니다. 둘 다 불가능하면 F2를 적용하지 말고 **판정 보류**로 기록합니다 |
| P4 | 주문 API가 주문을 저장하고 포인트를 차감함 | 주문 후 잔액 확인(P3와 같은 수단). 데이터 수집 플랫폼 전송은 여기서 보지 않고 C2에서 판정 |
| P5 | 인기 메뉴 API가 최근 7일 기준 인기 메뉴 3개를 응답함 | 메뉴가 4개 이상이면 4개 이상을 횟수를 다르게 주문한 뒤 상위 3개가 맞는지 확인. 메뉴가 3개 이하이면 주문 횟수 순서만 확인 |
| P6 | README에 설계 내용(ERD, API 명세서), 설계 의도, 문제 해결 전략과 분석 내용, 기술 선택 이유가 있음 | README 확인 |

- P5와 B3에서 **인기의 기준은 주문 횟수(건수)** 입니다. 지원자 README 3-4가 "메뉴별 주문 횟수가 정확해야 합니다"라고 정하고 있습니다. 지원자가 다른 기준(예: 매출액)을 썼다면 제출 README에 근거가 있는지 확인하고 **판정 보류**로 기록합니다.

## 3. 영역별 기준

### A. 다수 인스턴스 (25점)

도전 요구사항 1: 애플리케이션이 다수의 서버에서 다수의 인스턴스로 동작해도 기능에 문제가 없어야 합니다.

| ID | 판정 질문 | 배점 | 기준 |
|---|---|---|---|
| A1 | 상태를 서버 메모리에 두지 않는가 | 10 | 포인트 잔액, 주문 내역, 인기 메뉴 집계가 모든 서버가 함께 보는 저장소(DB, Redis 등)에 있으면 만점입니다. `HashMap`, `static` 필드, 로컬 캐시에 원본 데이터를 두면 0점입니다. 판정 대상은 **포인트 잔액, 주문 내역, 인기 메뉴 집계** 세 가지 원본 데이터뿐이며, 데이터 수집 플랫폼 Mock의 수신 내역은 대상이 아닙니다(정답의 `MockDataPlatformClient`도 `ConcurrentHashMap`을 씁니다). |
| A2 | 동시성 제어 수단이 서버 여러 대에서도 효과가 있는가 | 10 | DB 락(비관적 락, 낙관적 락), 조건부 UPDATE, 분산 락처럼 서버 밖에서 동작하는 방법이면 만점입니다. `synchronized`, `ReentrantLock`, `ConcurrentHashMap` 같은 JVM 안의 락만 쓰면 0점입니다. JVM 락은 서버 1대에서는 B 영역 시나리오를 통과하지만 서버가 2대가 되면 막지 못하므로, B 영역 결과와 관계없이 0점입니다. 판정 대상은 **포인트 잔액과 주문을 보호하는 동시성 제어 수단**이며, 그 밖의 용도로 쓴 `ConcurrentHashMap` 등은 보지 않습니다. |
| A3 | README에 다수 인스턴스 관점의 설명이 있는가 | 5 | 고른 방법이 **서버 여러 대에서도 동작하는 이유**가 적혀 있으면 5점, 기술 이름만 적혀 있으면 2점, 설명이 없으면 0점입니다. 지원자 README 4장이 요구한 **락·트랜잭션의 범위와 해제 순서**도 여기서 함께 봅니다 — 서술이 있고 코드와 일치하면 5점 기준을 충족한 것으로 보고, 서술과 코드가 다르면 2점으로 내립니다. JVM 락의 한계나 스케줄러 중복 실행까지 다뤘다면 우수 사례로 기록합니다(가점은 없습니다). |

### B. 동시성 (25점)

도전 요구사항 2: 동시성 이슈를 고려해 구현해야 합니다.

| ID | 시나리오 | 배점 | 통과 기준 |
|---|---|---|---|
| B1 | 메뉴 하나의 3잔 값만 충전한 사용자가 그 메뉴 주문 10건을 동시에 보냄 | 10 | **성공 건수 × 가격 = 차감된 포인트**이고, 성공이 **3건을 넘지 않으며**, 잔액이 음수가 아니면 통과입니다(보통 3건 성공·7건 실패·잔액 0). 성공이 3건보다 적으면 실패한 요청이 재시도 가능한 응답(409 등)을 받았는지 확인하고, 받았으면 감점하지 않습니다(B2와 같은 원칙). 재시도할 수 없는 응답(500 등)을 받았다면 **5점**으로 기록합니다 — 잔액은 지켜졌지만 정상 요청까지 잃은 것이므로 만점은 아닙니다. **4건 이상 성공하거나 잔액이 음수가 되면** 치명 오류 F3입니다. |
| B2 | 같은 사용자에게 100P 충전 100건을 동시에 보냄 | 5 | 최종 잔액이 **성공한 충전 금액의 합**과 같아야 합니다(예: 100건 모두 성공하면 10,000P). 실패한 요청이 있다면 그 요청이 클라이언트가 재시도할 수 있는 응답(409, 429, 503 등 — 분산 락 대기 초과를 503으로 주는 설계를 포함)을 받았는지 확인하세요 — 명세는 "잔액이 틀어지지 않는 것"만 요구하므로, 재시도 가능한 응답을 받고 실패한 건은 감점하지 않습니다. 성공했다고 응답했는데 잔액에 반영되지 않은 충전이 있으면(응답과 잔액이 불일치) 0점입니다. |
| B3 | 서로 다른 사용자 50명이 같은 메뉴를 동시에 주문함 (평가 순서 3번에서 미리 충전해 둡니다) | 5 | 그 메뉴의 주문 횟수 **증가분이 50**이면 통과입니다(시나리오 전에 집계를 읽어 두고 비교합니다). 사용자를 50명 못 채웠으면 **보낸 건수와 증가분이 같은지**로 판정합니다. 증가분이 모자라면 0점입니다. 응답에 횟수가 없으면 코드와 저장소를 보고 판정합니다. |
| B4 | 락의 범위가 적절한가 | 5 | 사용자 단위처럼 필요한 범위만 잠갔으면 만점입니다. 모든 주문과 충전을 락 하나로 처리하면 B1, B2를 통과해도 2점입니다. 조건부 UPDATE처럼 락 없이 해결했다면 만점입니다. |

- B1 셋업 주의: 지원자가 충전 금액에 제약(예: 1,000원 단위)을 두었으면 3잔 값을 정확히 만들지 못할 수 있습니다. 그때는 잔액을 **3잔 값 이상 4잔 값 미만**으로 맞추고 "성공 3건, 잔액 = 충전액 − 가격 × 3"으로 판정합니다. 그것도 안 되면 `성공 건수 × 가격 ≤ 충전액`과 잔액이 음수가 아닌지만 봅니다. 이때 **성공이 3건을 넘었다는 이유만으로는 F3을 적용하지 않습니다**(셋업 때문이므로). 다만 **잔액이 음수면 이 경우에도 F3**입니다.
- B2 셋업 주의: 충전 금액에 제약이 있으면 100P 대신 **허용되는 최소 단위**로 100건을 보냅니다. 제약 때문에 400이 돌아오는 것은 재시도 가능한 실패로 보지 않고, 금액을 바꿔 다시 측정합니다.

### C. 데이터 일관성 (25점)

도전 요구사항 3: 데이터 일관성을 고려해 구현해야 합니다.

| ID | 판정 질문 | 배점 | 기준 |
|---|---|---|---|
| C1 | 포인트 차감과 주문 저장이 한 트랜잭션으로 묶여 있는가 | 10 | 둘 중 하나만 저장되는 경우가 없어야 합니다. 포인트는 빠졌는데 주문이 없거나, 주문은 있는데 포인트가 그대로인 상태가 생길 수 있으면 0점입니다. 분산 락을 쓴다면 락 해제가 커밋 뒤에 일어나는지도 봅니다. 커밋 전에 락을 풀면 5점입니다. |
| C2 | 데이터 수집 플랫폼 전송이 결제와 어긋나지 않는가 | 10 | 먼저 지원자 README 3-3이 요구한 **사용자 식별값, 메뉴 ID, 결제 금액**이 실제로 전송되는지 Mock이나 테스트에서 확인합니다(빠진 값이 있으면 한 등급 낮춤). 그다음 아래 기준으로 판정합니다. |
| C3 | 인기 메뉴 집계가 실제 주문과 맞는가 | 5 | 커밋된 주문만 집계에 반영되면 만점입니다. 트랜잭션 안에서 집계를 먼저 올려 롤백된 주문이 집계에 남을 수 있으면 2점입니다. 집계 원천을 캐시(Redis 등)로 둔 경우, 캐시가 비었을 때 주문 테이블로 되돌아오는 경로가 있는지 확인하세요. 없으면 3점입니다. 두 조건이 함께 해당하면 합산하지 않고 낮은 쪽인 **2점**으로 기록합니다. |

C2 판정 기준

- 명세 3-3은 "실시간 전송"만 요구하고 전송 실패 시의 처리는 정하지 않았습니다. 그래서 **전송 위치(트랜잭션 안/밖)만 보고 기계적으로 감점하지 말고**, 그 선택의 근거가 제출 README에 적혀 있는지를 함께 보세요. 트랜잭션 안에서 동기로 호출했더라도 "왜 그렇게 읽었는지"와 "그 방식의 한계"가 적혀 있으면 **중(6점)**입니다.
- **상(10점)의 전송 실패 대책**은 지원자 문서가 직접 요구한 것이 아니라 도전 요구사항 3(데이터 일관성)에서 끌어낸 것입니다. 없다고 해서 감점이 아니라, 있을 때 상으로 올리는 기준입니다.

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 10 | 커밋된 뒤에 전송하고(`@TransactionalEventListener` 등), 전송 실패에 대한 대책(아웃박스 테이블과 재전송, 실패 기록 등)이 있습니다. |
| 중 | 6 | 커밋된 뒤에 전송하지만 실패하면 로그만 남기고 끝납니다. **또는** 트랜잭션 안에서 동기로 호출하지만, "실시간 요구를 그렇게 읽었고 전송 실패 시 결제도 함께 롤백된다"는 판단이 README에 적혀 있습니다. |
| 하 | 2 | 전송 위치에 대한 판단이 코드와 README 어디에도 없습니다(트랜잭션 안 동기 호출인데 근거도 없는 경우 포함). |
| 없음 | 0 | 전송 로직이 없습니다. |

- 실시간 전송의 기준: 주문 요청과 같은 흐름에서 바로 전송을 시작하면 인정합니다. 하루 한 번 모아서 보내는 배치 방식은 실시간이 아니므로 중 이하로 판정합니다.

### D. 테스트 (25점)

도전 요구사항 4: 각 기능과 제약사항에 대한 테스트를 작성해야 합니다.

| ID | 판정 질문 | 배점 | 기준 |
|---|---|---|---|
| D1 | 기능 테스트가 있는가 | 8 | API 4개 각각에 대해 정상 동작을 확인하는 테스트가 있으면 만점입니다. 하나 빠질 때마다 2점씩 뺍니다. |
| D2 | 동시성 테스트가 있는가 | 10 | 여러 스레드로 동시에 요청하는 테스트로 B1(잔액 초과 결제 방지), B2(충전 누락 방지), B3(주문 횟수 정확성) 중 2개 이상을 확인하면 만점, 1개면 5점입니다. |
| D3 | 제약사항과 실패 상황 테스트가 있는가 | 7 | 포인트 부족, 없는 메뉴, 잘못된 충전 금액, 최근 7일 범위, 처리 중 실패 시 롤백, 외부 전송 실패 같은 상황 중 3개 이상을 확인하면 만점, 1~2개면 3점입니다. |

- `./gradlew test`가 실패하면 실패한 테스트는 없는 것으로 보고 판정합니다. Docker가 필요한 테스트(Testcontainers 등)는 Docker를 켜고 실행합니다.
- 서버 2대를 띄워 확인하는 테스트가 있으면 우수 사례로 기록합니다. 정답 코드의 `MultiInstanceTest`가 예시입니다.

## 4. 판정 보류 기준

- 이 과제는 정해진 정답이 없습니다. 기준표에 없는 방법을 썼다면, 그 방법이 서버 여러 대에서도 같은 결과를 내는지와 README에 이유가 있는지를 보고 판단합니다.
- 판정이 애매하면 낮은 점수를 주지 말고 **판정 보류**로 기록한 뒤 이유를 남깁니다.

## 6. 인정하는 다른 풀이

| 방법 | 판정 |
|---|---|
| DB 비관적 락(`SELECT ... FOR UPDATE`)으로 사용자 포인트 행을 잠금 | A2, B4 만점. Redis 없이 DB만으로도 다수 인스턴스를 만족합니다. |
| 조건부 UPDATE(`UPDATE ... SET balance = balance - ? WHERE user_id = ? AND balance >= ?`) | A2, B4 만점. 영향받은 행 수로 잔액 부족을 판정하면 됩니다. |
| 낙관적 락(`@Version`) | A2 만점. 재시도를 붙이면 B2에서도 만점 가능. 재시도 없이 충돌한 요청을 그대로 실패시켜도, 그 응답이 재시도 가능한 4xx/409이고 잔액이 성공한 건과 일치하면 B2는 위 기준대로 감점하지 않습니다. |
| 인기 메뉴를 주문 테이블 집계 쿼리(GROUP BY)로 계산 | B3, C3 만점. 정확성은 Redis 집계보다 높습니다. 조회 성능에 대한 고민이 README에 있으면 우수 사례로 기록합니다. |
| 메시지 큐(Kafka 등)로 데이터 수집 플랫폼에 전송 | C2는 커밋 뒤에 발행하는지와 발행 실패 대책으로 판정합니다. |
