# 과제 5. 커피숍 주문 시스템 평가 기준표

> 튜터용 문서, v1.0 (2026-10-19)
> - 수강생 README의 도전 요구사항 4가지(다수 인스턴스, 동시성, 데이터 일관성, 테스트)를 기준으로 채점합니다.
> - 필수 API 4개와 README의 문제 해결 전략은 채점 전에 확인하는 전제 조건입니다.
> - 같은 폴더의 `solution/`(정답 서버)을 함께 사용합니다.

---

## 1. 배점 요약

| 영역 | 배점 | 판정 방법 |
|---|---|---|
| A. 다수 인스턴스 | 25 | 코드와 README를 읽고 판정. 가능하면 서버 2대를 띄워 확인 |
| B. 동시성 | 25 | 튜터가 동시 요청을 직접 보내 확인하고, 코드로 락 범위 판정 |
| C. 데이터 일관성 | 25 | 코드를 읽고 트랜잭션 경계와 외부 전송 위치를 판정 |
| D. 테스트 | 25 | 수강생 테스트 코드를 읽고 `./gradlew test`로 실행 |
| **합계** | **100** | |

- 이 과제는 API 명세를 수강생이 직접 정합니다. 요청을 보낼 때는 수강생 README의 API 명세를 따릅니다.

### 평가 순서

1. 2장의 전제 조건을 확인합니다.
2. 수강생 README에 적힌 방법으로 서버와 인프라를 실행합니다.
3. 3장 B 영역의 동시 요청 시나리오를 보냅니다.
4. 코드와 README를 읽고 A, C 영역을 판정합니다.
5. `./gradlew test`를 실행하고 D 영역을 판정합니다.
6. 5장의 치명 오류가 있는지 확인합니다.

> **동시 요청 보내는 방법**
> - 셸에서 `for i in $(seq 1 10); do curl -s -o /dev/null -w "%{http_code}\n" -X POST ... & done; wait`처럼 `&`를 붙여 요청을 동시에 보냅니다.
> - 응답 코드별 개수와 이후 잔액, 주문 수, 인기 메뉴 결과를 확인합니다.
>
> **서버 2대로 확인하는 방법 (A 영역, 선택)**
> - 수강생 서버를 포트만 바꿔 두 번 실행합니다. (예: `SERVER_PORT=8081`처럼 수강생 README가 안내한 방법)
> - 위 동시 요청을 두 포트에 번갈아 보냅니다. 두 서버가 같은 DB와 저장소를 보지 않으면 이 단계는 건너뛰고 코드로만 판정합니다.
>
> **정답 서버와 비교하는 방법**
> - 판정이 애매하면 `solution/`을 실행하고 같은 시나리오를 보내 기대 동작을 확인합니다. 실행 방법은 `solution/README.md`에 있습니다.

## 2. 전제 조건

채점을 시작하기 전에 아래 항목을 확인합니다. 빠진 항목은 5장 치명 오류에 따라 처리합니다.

| ID | 확인 항목 | 확인 방법 |
|---|---|---|
| P1 | 서버가 수강생 README의 안내대로 실행됨 | README의 실행 방법을 그대로 따라 함 |
| P2 | 메뉴 목록 조회 API가 메뉴 ID, 이름, 가격을 응답함 | 요청을 보내 확인 |
| P3 | 포인트 충전 API가 사용자 식별값과 충전 금액으로 충전함 (1원 = 1P) | 충전 후 잔액 확인 |
| P4 | 주문 API가 포인트를 차감하고 주문 내역을 데이터 수집 플랫폼(Mock)으로 전송함 | 주문 후 잔액과 로그, 또는 Mock 수신 결과 확인 |
| P5 | 인기 메뉴 API가 최근 7일 기준 인기 메뉴 3개를 응답함 | 메뉴 4개 이상을 횟수를 다르게 주문한 뒤 확인 |
| P6 | README에 설계 내용(ERD, API 명세서), 설계 의도, 문제 해결 전략과 분석 내용, 기술 선택 이유가 있음 | README 확인 |

## 3. 영역별 기준

### A. 다수 인스턴스 (25점)

도전 요구사항 1: 애플리케이션이 다수의 서버에서 다수의 인스턴스로 동작해도 기능에 문제가 없어야 합니다.

| ID | 판정 질문 | 배점 | 기준 |
|---|---|---|---|
| A1 | 상태를 서버 메모리에 두지 않는가 | 10 | 포인트 잔액, 주문 내역, 인기 메뉴 집계가 모든 서버가 함께 보는 저장소(DB, Redis 등)에 있으면 만점입니다. `HashMap`, `static` 필드, 로컬 캐시에 원본 데이터를 두면 0점입니다. |
| A2 | 동시성 제어 수단이 서버 여러 대에서도 효과가 있는가 | 10 | DB 락(비관적 락, 낙관적 락), 조건부 UPDATE, 분산 락처럼 서버 밖에서 동작하는 방법이면 만점입니다. `synchronized`, `ReentrantLock`, `ConcurrentHashMap` 같은 JVM 안의 락만 쓰면 0점입니다. 서버 1대에서는 B 영역 시나리오를 통과해도 이 항목은 0점입니다. |
| A3 | README에 다수 인스턴스 관점의 설명이 있는가 | 5 | JVM 락으로는 다른 서버의 요청을 막을 수 없다는 점과, 고른 방법이 서버 여러 대에서도 동작하는 이유가 있으면 만점입니다. 스케줄러나 재시도 작업이 서버마다 중복 실행되는 문제까지 다뤘다면 우수 사례로 기록합니다. |

### B. 동시성 (25점)

도전 요구사항 2: 동시성 이슈를 고려해 구현해야 합니다.

| ID | 시나리오 | 배점 | 통과 기준 |
|---|---|---|---|
| B1 | 메뉴 하나의 3잔 값만 충전한 사용자가 그 메뉴 주문 10건을 동시에 보냄 | 10 | **3건만 성공**, 나머지 7건은 실패. 이후 잔액 0, 주문 3건. 4건 이상 성공하거나 잔액이 음수가 되면 이 항목은 0점이고 치명 오류 F3에 해당합니다. |
| B2 | 같은 사용자에게 100P 충전 100건을 동시에 보냄 | 5 | 100건 모두 성공하고 잔액이 **10,000P**. 일부 충전이 사라지면 0점입니다. |
| B3 | 서로 다른 사용자 50명이 같은 메뉴를 동시에 주문함 | 5 | 인기 메뉴 결과에서 그 메뉴의 주문 횟수가 **50**. 숫자가 모자라면 0점입니다. 응답에 횟수가 없으면 코드와 저장소를 보고 판정합니다. |
| B4 | 락의 범위가 적절한가 | 5 | 사용자 단위처럼 필요한 범위만 잠갔으면 만점입니다. 모든 주문과 충전을 락 하나로 처리하면 B1, B2를 통과해도 2점입니다. 조건부 UPDATE처럼 락 없이 해결했다면 만점입니다. |

### C. 데이터 일관성 (25점)

도전 요구사항 3: 데이터 일관성을 고려해 구현해야 합니다.

| ID | 판정 질문 | 배점 | 기준 |
|---|---|---|---|
| C1 | 포인트 차감과 주문 저장이 한 트랜잭션으로 묶여 있는가 | 10 | 둘 중 하나만 저장되는 경우가 없어야 합니다. 포인트는 빠졌는데 주문이 없거나, 주문은 있는데 포인트가 그대로인 상태가 생길 수 있으면 0점입니다. 분산 락을 쓴다면 락 해제가 커밋 뒤에 일어나는지도 봅니다. 커밋 전에 락을 풀면 5점입니다. |
| C2 | 데이터 수집 플랫폼 전송이 결제와 어긋나지 않는가 | 10 | 아래 기준으로 판정합니다. |
| C3 | 인기 메뉴 집계가 실제 주문과 맞는가 | 5 | 커밋된 주문만 집계에 반영되면 만점입니다. 트랜잭션 안에서 집계를 먼저 올려 롤백된 주문이 집계에 남을 수 있으면 2점입니다. |

C2 판정 기준

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 10 | 커밋된 뒤에 전송하고(`@TransactionalEventListener` 등), 전송 실패에 대한 대책(아웃박스 테이블과 재전송, 실패 기록 등)이 있습니다. |
| 중 | 6 | 커밋된 뒤에 전송하지만 실패하면 로그만 남기고 끝납니다. 또는 대책은 있지만 트랜잭션 안에서 전송합니다. |
| 하 | 2 | 트랜잭션 안에서 동기로 호출해, 전송이 실패하면 결제까지 롤백되거나 롤백된 주문도 전송됩니다. |
| 없음 | 0 | 전송 로직이 없습니다. (전제 조건 P4 미충족) |

- 실시간 전송의 기준: 주문 요청과 같은 흐름에서 바로 전송을 시작하면 인정합니다. 하루 한 번 모아서 보내는 배치 방식은 실시간이 아니므로 중 이하로 판정합니다.

### D. 테스트 (25점)

도전 요구사항 4: 각 기능과 제약사항에 대한 테스트를 작성해야 합니다.

| ID | 판정 질문 | 배점 | 기준 |
|---|---|---|---|
| D1 | 기능 테스트가 있는가 | 8 | API 4개 각각에 대해 정상 동작을 확인하는 테스트가 있으면 만점입니다. 하나 빠질 때마다 2점씩 뺍니다. |
| D2 | 동시성 테스트가 있는가 | 10 | 여러 스레드로 동시에 요청하는 테스트로 B1(잔액 초과 결제 방지), B2(충전 누락 방지), B3(주문 횟수 정확성) 중 2개 이상을 확인하면 만점, 1개면 5점입니다. |
| D3 | 제약사항과 실패 상황 테스트가 있는가 | 7 | 포인트 부족, 없는 메뉴, 잘못된 충전 금액, 최근 7일 범위, 처리 중 실패 시 롤백, 외부 전송 실패 같은 상황 중 3개 이상을 확인하면 만점, 1~2개면 3점입니다. |

- `./gradlew test`가 실패하면 실패한 테스트는 없는 것으로 보고 판정합니다. Docker가 필요한 테스트(Testcontainers 등)는 Docker를 켜고 실행합니다.
- 서버 2대를 띄워 확인하는 테스트가 있으면 우수 사례로 기록합니다. 정답 코드의 `MultiInstanceTest`가 예시입니다.

## 4. 판정 보류 기준

- 이 과제는 정해진 정답이 없습니다. 기준표에 없는 방법을 썼다면, 그 방법이 서버 여러 대에서도 같은 결과를 내는지와 README에 이유가 있는지를 보고 판단합니다.
- 판정이 애매하면 낮은 점수를 주지 말고 **판정 보류**로 기록한 뒤 이유를 남깁니다.

## 6. 인정하는 다른 풀이

| 방법 | 판정 |
|---|---|
| DB 비관적 락(`SELECT ... FOR UPDATE`)으로 사용자 포인트 행을 잠금 | A2, B4 만점. Redis 없이 DB만으로도 다수 인스턴스를 만족합니다. |
| 조건부 UPDATE(`UPDATE ... SET balance = balance - ? WHERE user_id = ? AND balance >= ?`) | A2, B4 만점. 영향받은 행 수로 잔액 부족을 판정하면 됩니다. |
| 낙관적 락(`@Version`)과 재시도 | A2 만점. 재시도 없이 충돌한 요청을 모두 실패시키면 B2에서 충전이 실패하므로, B2 기준(100건 모두 성공)을 그대로 적용합니다. |
| 인기 메뉴를 주문 테이블 집계 쿼리(GROUP BY)로 계산 | B3, C3 만점. 정확성은 Redis 집계보다 높습니다. 조회 성능에 대한 고민이 README에 있으면 우수 사례로 기록합니다. |
| 메시지 큐(Kafka 등)로 데이터 수집 플랫폼에 전송 | C2는 커밋 뒤에 발행하는지와 발행 실패 대책으로 판정합니다. |
