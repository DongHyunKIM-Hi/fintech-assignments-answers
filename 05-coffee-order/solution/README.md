# 과제 5. 커피숍 주문 시스템 정답 코드

- 지원자 README의 필수 요구사항과 도전 요구사항 4가지를 구현한 참고 구현입니다.
- 이 README의 구성(설계 내용, 설계 의도, 문제 해결 전략, 기술 선택 이유)은 지원자 README 3-0에서 요구하는 내용의 예시이기도 합니다.
- 정답은 하나가 아닙니다. DB 락이나 조건부 UPDATE만으로 풀어도 됩니다. 인정하는 다른 풀이는 `평가기준표.md` 6장에 있습니다.

## 실행 방법

MySQL과 Redis를 먼저 띄운 뒤 서버를 실행합니다. Docker가 필요합니다.

```bash
docker compose up -d --wait # MySQL 8.4 (3306), Redis 7.4 (6379). 준비가 끝날 때까지 기다림
./gradlew bootRun           # 서버 1, 포트 8080
```

서버 2대로 확인하려면 다른 터미널에서 포트만 바꿔 한 번 더 실행합니다.

```bash
SERVER_PORT=8081 ./gradlew bootRun
```

- 테이블과 메뉴 데이터는 서버가 시작될 때 `schema.sql`, `data.sql`로 만들어집니다.
- 데이터 수집 플랫폼은 `MockDataPlatformClient`가 대신합니다. 받은 주문은 서버 로그에 `[데이터 수집 플랫폼] 주문 수신`으로 찍힙니다.

## 1. 설계 내용

### API 명세

| 기능 | 요청 | 성공 응답 |
|---|---|---|
| 메뉴 목록 조회 | `GET /api/menus` | 200 `[{"menuId":1,"name":"아메리카노","price":4500}, ...]` |
| 포인트 충전 | `POST /api/points/charge` `{"userId":1,"amount":10000}` | 200 `{"userId":1,"balance":10000}` |
| 포인트 조회 | `GET /api/points/{userId}` | 200 `{"userId":1,"balance":10000}` (확인용으로 추가) |
| 주문과 결제 | `POST /api/orders` `{"userId":1,"menuId":1}` | 201 `{"orderId":1,"menuId":1,"menuName":"아메리카노","paidAmount":4500,"remainingPoint":5500,"orderedAt":"..."}` |
| 인기 메뉴 조회 | `GET /api/menus/popular` | 200 `[{"rank":1,"menuId":2,"name":"카페라떼","price":5000,"orderCount":12}, ...]` (오늘 포함 최근 7일, 최대 3개) |

에러 응답은 모두 `{"code":"...","message":"..."}` 형식입니다.

| 상황 | 상태 코드 | code |
|---|---|---|
| 필수값 누락, 형식 오류, 0원 이하 충전, 소수 금액, 1회 충전 한도(100만 원) 초과 | 400 | `INVALID_REQUEST` |
| 없는 메뉴 주문 | 404 | `MENU_NOT_FOUND` |
| 포인트 부족 | 409 | `INSUFFICIENT_POINT` |
| 같은 사용자의 앞선 요청이 5초 넘게 끝나지 않음 | 503 | `REQUEST_BUSY` |
| Redis 장애 등 예상하지 못한 오류 | 500 | `INTERNAL_ERROR` |

- 없는 경로(404)나 지원하지 않는 메서드(405)도 같은 형식으로 응답합니다.
- 금액에 `10.5`처럼 소수가 오면 잘라서 받지 않고 400으로 거절합니다(`spring.jackson.deserialization.accept-float-as-int: false`).

### ERD

```
menu                    user_point               coffee_order               order_event (아웃박스)
--------------------    ---------------------    -----------------------    ------------------------
id     PK               user_id    PK            id          PK             id            PK
name                    balance    (>= 0)        user_id                    order_id      UNIQUE
price                   updated_at               menu_id                    user_id, menu_id, amount
                                                 price                      status (PENDING, SENT)
                                                 ordered_at  (인덱스)        attempt_count
                                                                            created_at, sent_at
                                                                            (status, created_at 인덱스)
```

- `coffee_order.price`는 주문 시점의 메뉴 가격입니다. 나중에 메뉴 가격이 바뀌어도 결제 금액은 그대로 남습니다.
- `user_point.balance`에는 `CHECK (balance >= 0)` 제약을 걸었습니다. 코드의 실수로 락이 빠져도 DB가 음수 잔액을 막습니다.
- 사용자 테이블은 만들지 않았습니다. 요구사항이 사용자 식별값만 받으므로, 첫 충전 때 `user_point` 행을 만듭니다.

### 구조

- 서버는 여러 대 실행되고, 모두 같은 MySQL과 Redis를 봅니다.
- MySQL에는 메뉴, 포인트, 주문, 전송할 이벤트를 저장합니다. 원본 데이터는 모두 MySQL에 있습니다.
- Redis는 두 가지에 씁니다. 사용자 단위 분산 락(Redisson)과 날짜별 인기 메뉴 집계(정렬 집합)입니다.

## 2. 설계 의도와 문제 해결 전략

도전 요구사항 4가지에 하나씩 대응합니다.

### 도전 1. 다수 서버, 다수 인스턴스

- 서버 메모리에는 아무 상태도 두지 않습니다. 잔액, 주문, 집계는 모두 MySQL이나 Redis에 있으므로 어느 서버로 요청이 가도 결과가 같습니다.
- `synchronized`는 한 서버 안의 스레드만 막습니다. 같은 사용자의 요청이 서버 1과 서버 2로 동시에 들어오면 둘 다 통과합니다. 그래서 락을 Redis에 둡니다(`DistributedLockExecutor`).
- 실패한 전송을 다시 보내는 스케줄러도 서버마다 돕니다. 같은 이벤트를 여러 서버가 동시에 보내지 않도록, Redis 락을 잡은 서버 한 대만 실행하고 나머지는 이번 차례를 건너뜁니다(`OrderEventRetryScheduler`).

### 도전 2. 동시성

| 문제 | 해결 |
|---|---|
| 같은 사용자의 주문이 동시에 들어와 잔액을 둘 다 통과함 | 충전과 주문이 같은 락 `point:{userId}`를 잡고, 그 안에서 잔액 확인과 차감을 합니다. |
| 같은 사용자의 충전이 동시에 들어와 일부가 사라짐 | 충전도 같은 락 안에서 처리합니다. 처음 충전하는 사용자의 행을 두 서버가 동시에 만들려는 문제도 함께 막힙니다. |
| 같은 메뉴가 동시에 주문되어 집계가 빠짐 | Redis `ZINCRBY`는 Redis 안에서 원자적으로 실행되므로 락 없이도 횟수가 빠지지 않습니다. |

- 락의 범위는 사용자 한 명입니다. 다른 사용자의 요청은 서로 기다리지 않습니다.
- 락은 트랜잭션보다 바깥에 있어야 합니다. 락 획득, 트랜잭션 시작, 커밋, 락 해제 순서입니다. `@Transactional` 메서드 안에서 락을 잡고 풀면, 락이 풀린 뒤 커밋되기 전에 다음 요청이 이전 잔액을 읽을 수 있습니다. 그래서 락 안에서 `TransactionTemplate`으로 트랜잭션을 엽니다.
- 락에 임대 시간을 정하지 않아 Redisson이 작업이 끝날 때까지 락 만료를 자동으로 늘립니다. 서버가 죽으면 연장이 멈추고 30초 뒤 락이 풀립니다.

### 도전 3. 데이터 일관성

주문 한 건에서 바뀌는 데이터는 네 곳입니다. 묶는 방법을 다르게 했습니다.

| 데이터 | 시점 | 실패하면 |
|---|---|---|
| 포인트 차감, 주문 저장, 전송할 이벤트 저장 (MySQL) | 한 트랜잭션 | 셋 다 롤백됩니다. 돈은 빠졌는데 주문이 없는 상태가 생기지 않습니다. |
| 인기 메뉴 집계 (Redis) | 커밋된 뒤 | 결제는 유지하고 로그를 남깁니다. 조회할 때 Redis에 장애가 있으면 주문 테이블을 직접 집계합니다. |
| 데이터 수집 플랫폼 전송 (외부) | 커밋된 뒤, 별도 스레드 | 이벤트가 `PENDING`으로 남고, 스케줄러가 10초마다 다시 보냅니다. |

- 외부 전송을 트랜잭션 안에서 하면 두 가지 문제가 생깁니다. 플랫폼이 느리면 락과 DB 연결을 오래 잡고, 전송 뒤에 롤백되면 없는 주문을 보낸 셈이 됩니다. 그래서 커밋된 뒤에 보냅니다(`@TransactionalEventListener`).
- 커밋 직후 서버가 죽으면 전송이 빠질 수 있습니다. 이를 막으려고 보낼 이벤트를 주문과 같은 트랜잭션에 저장합니다(아웃박스 패턴). 주문이 있으면 보낼 이벤트도 반드시 있습니다.
- 같은 이벤트가 두 번 전송될 수 있습니다(비동기 전송과 재전송이 겹치는 경우). 그래서 이벤트 ID를 함께 보내 받는 쪽이 중복을 거를 수 있게 했습니다. 한 번은 반드시 보내고, 두 번 보낼 수도 있는 방식입니다.
- 인기 메뉴 집계도 커밋된 뒤에 올립니다. 트랜잭션 안에서 먼저 올리면 롤백된 주문이 집계에 남습니다.

> [!NOTE]
> **알고 있는 한계**
> - 커밋 직후 Redis 집계를 올리기 전에 서버가 죽으면, 그 주문 한 건이 인기 메뉴 집계에서 빠집니다. 주문 테이블에는 남아 있으므로 집계를 다시 계산할 수 있습니다.
> - 이를 완전히 막으려면 집계 반영도 아웃박스 이벤트로 처리해야 합니다. 이 과제에서는 구조가 커지는 것에 비해 얻는 것이 적어 넣지 않았습니다.
> - 분산 락도 Redis에 있으므로, Redis 전체가 멈추면 충전과 주문은 약 5초 뒤 500으로 실패합니다. 포인트는 빠지지 않습니다. 메뉴 조회는 그대로 되고, 인기 메뉴 조회는 2초 안에 주문 테이블 집계로 대신 응답합니다(Redis 응답 대기 시간 2초).

## 3. 기술 선택 이유

| 기술 | 이유 | 고려한 다른 방법 |
|---|---|---|
| MySQL | 포인트와 주문은 돈과 관련된 원본 데이터라 트랜잭션이 필요합니다. | 없음 |
| Redis 분산 락 (Redisson) | 서버가 여러 대여도 같은 사용자의 잔액 변경을 하나씩 처리합니다. 락 만료 자동 연장과 대기 기능을 직접 만들지 않아도 됩니다. | DB 비관적 락, 조건부 UPDATE. 이 두 방법도 서버 여러 대에서 동작합니다. 이 과제는 Redis를 집계에도 쓰므로 락도 Redis에 두었습니다. |
| Redis 정렬 집합 | 날짜별 키에 `ZINCRBY`로 횟수를 쌓고, 조회할 때 7개 키를 합칩니다. 주문이 쌓여도 조회 비용이 늘지 않습니다. | 주문 테이블 `GROUP BY`. 정확하지만 주문이 많아지면 조회할 때마다 7일 치를 읽습니다. Redis 장애 때의 대안으로 남겨 두었습니다. |
| 아웃박스 테이블 | 주문과 보낼 이벤트를 한 트랜잭션에 저장해, 전송이 실패하거나 서버가 죽어도 이벤트가 사라지지 않습니다. | 메시지 큐(Kafka). 인프라가 하나 더 늘어나고, 큐에 발행하는 단계에서 같은 문제가 다시 생깁니다. |

## 패키지 구조

```
com.practicefintech.coffee
├── CoffeeApplication.java
├── common/
│   ├── entity/       # Menu, UserPoint, CoffeeOrder, OrderEvent
│   ├── enums/        # ErrorCode, OrderEventStatus
│   ├── exception/    # ApiException, ErrorResponse, GlobalExceptionHandler
│   ├── config/       # ClockConfig, RedissonConfig
│   └── lock/         # DistributedLockExecutor (분산 락 + 트랜잭션)
└── domain/
    ├── menu/         # 메뉴 조회, 인기 메뉴 (PopularMenuRanking: Redis 집계)
    ├── point/        # 포인트 충전과 조회
    ├── order/        # 주문과 결제 (OrderService), 주문과 이벤트 저장소
    └── dataplatform/ # 데이터 수집 플랫폼 Mock, 전송(OrderEventSender), 재전송 스케줄러
```

- 시간은 `Clock` 빈으로 받습니다. 인기 메뉴의 날짜 계산을 테스트에서 확인하기 위해서입니다.
- DTO는 다른 과제의 정답 코드와 같이 Lombok을 사용한 일반 클래스로 작성했습니다.
