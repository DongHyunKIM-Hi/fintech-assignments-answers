# 단계별 구현 — 카페 주문 시스템

해설 영상에서 **한 번에 완성하지 않고 세 단계로 나눠** 만들어 가기 위한 코드입니다.
각 단계는 그대로 실행되는 프로젝트이고, 다음 단계는 앞 단계에 얹는 구조입니다.
패키지 구조, DTO, `build.gradle`, `schema.sql`, `data.sql`은 세 단계가 모두 같습니다.

| 단계 | 폴더 | 한 문장 |
|---|---|---|
| 1 | `step1-정상경로/` | API 4개가 DB로 돌아가는지만 확인합니다. 검증도 트랜잭션도 없습니다. |
| 2 | `step2-예외처리/` | 입력 검증·에러 응답·트랜잭션·외부 전송·7일 범위를 채웁니다. 아직 동시성은 깨집니다. |
| 3 | `../solution/` | 분산 락으로 동시성을, 아웃박스로 전송 실패를, Redis 집계와 폴백으로 조회를 해결합니다. |

## 실행 방법

MySQL과 Redis는 세 단계가 함께 씁니다. 1·2단계는 MySQL만 쓰지만, 같은 `compose.yaml`을 그대로 둡니다.

```bash
docker compose up -d --wait   # MySQL 8.4 (3306), Redis 7.4 (6379)
./gradlew bootRun             # 어느 단계 폴더에서든 동일
```

> [!IMPORTANT]
> `compose.yaml`은 세 폴더에 똑같이 들어 있지만, **컨테이너는 한 번만 띄웁니다.**
> `docker compose`는 폴더 이름으로 프로젝트를 구분하므로, 폴더를 옮겨 다시 `up` 하면
> 3306·6379 포트가 겹쳐 실패합니다. 단계를 바꿀 때는 **서버(`bootRun`)만 껐다 켜고**
> 컨테이너는 그대로 둡니다. 서버도 한 번에 하나만 띄웁니다(세 단계가 같은 DB를 씁니다).

- 테이블과 메뉴 데이터는 서버가 시작될 때 `schema.sql`, `data.sql`로 만들어집니다.
- API 경로와 요청·응답 형식은 세 단계가 모두 같습니다. 자세한 내용은 `../solution/README.md` 1장을 보세요.
- 1·2단계에는 테스트 코드가 없습니다. 테스트는 3단계에서 다룹니다(도전 요구사항 4).

> [!NOTE]
> `schema.sql`은 세 단계가 같으므로, 1·2단계에서도 `user_point`에 `CHECK (balance >= 0)` 제약이 걸려 있고
> 쓰지 않는 `order_event` 테이블(3단계의 아웃박스)이 만들어집니다. 일부러 그대로 둔 것입니다.
> 1단계에서 잔액이 음수가 되지 않는 이유가 바로 이 DB 제약이라는 점이 그 자체로 좋은 이야깃거리입니다.

## 1단계 — 정상 경로

**만드는 것**: 메뉴 목록 조회, 포인트 충전·조회, 주문과 결제, 인기 메뉴 조회. 네 API가 MySQL로 동작합니다.

**일부러 하지 않는 것**: 입력 검증, 에러 응답 형식, 잔액 확인, 트랜잭션, 데이터 수집 플랫폼 전송, 인기 메뉴의 7일 범위, 동시성 제어.

**실행하면 이렇게 됩니다** (포트 8151에서 실측)

| 확인 | 요청 | 결과 |
|---|---|---|
| 메뉴 목록 | `GET /api/menus` | 200, 메뉴 6개 |
| 충전 | `POST /api/points/charge` `{"amount":10000}` | 200 `{"balance":10000}` |
| 주문 | `POST /api/orders` `{"menuId":1}` (4,500원) | 201 `{"paidAmount":4500,"remainingPoint":5500}` |
| 인기 메뉴 | `GET /api/menus/popular` | 200, 상위 3개 |
| **잔액 부족** (500P로 4,500원 주문) | | **500** (`Internal Server Error`) — 잔액은 500 그대로. 막은 것은 애플리케이션이 아니라 DB의 `CHECK (balance >= 0)` |
| **없는 메뉴** (`menuId:999`) | | **500** (404여야 함 → 2단계) |
| **음수 충전** (`amount:-5000`) | | **200** — 잔액이 10,000 → **5,000**으로 **줄어듦** |
| **0원 충전** | | **200** |
| **소수 충전** (`amount:10.5`) | | **200** — 10으로 잘려서 충전됨 |
| **100만 원 초과 충전** (`2000000`) | | **200** — 그대로 충전됨 |
| **`amount` 누락** | | **500** (NullPointerException) |
| **포인트 행 없는 사용자 주문** | | **500** |
| **3잔 값(13,500P)으로 동시 10건 주문** | | **10건 모두 201**, 주문 10건 생성. 잔액은 **10회 중 8회 9,000 / 2회 4,500**으로 흔들립니다(트랜잭션이 없어 덮어쓰기 승자 수가 매번 다름). 공통점은 **13,500원으로 45,000원어치를 가져갔다**는 것입니다 |
| **100P 충전 100건 동시** | | 200 91건 / **500 9건**(`Duplicate entry ... for key 'user_point.PRIMARY'`) — 이 분포는 안정적입니다(8회 반복 모두 동일). 잔액은 **500·600·300**으로 흔들립니다 (9,100이어야 함) |
| **10일 전 주문 30건이 있는 메뉴** | `GET /api/menus/popular` | **집계에 포함됨**(`orderCount` 30, 최근 7일 조건이 없음). 몇 위인지는 DB에 쌓인 다른 주문 수에 따라 달라지므로 순위로 말하지 마세요 |

> 촬영 포인트: "일단 돌아간다"와 "요구사항을 만족한다"가 다르다는 것을 여기서 보여 줍니다.
> 특히 **음수 충전이 200으로 통과해 잔액이 줄어드는 것**과 **3잔 값으로 10잔을 가져가는 것**이 눈에 잘 띕니다.
> 동시 충전에서 나오는 500은 "처음 충전하는 사용자의 행을 여러 요청이 동시에 만들려다 기본 키가 충돌한 것"입니다.

## 2단계 — 예외 처리와 시나리오

**추가하는 것**
- `ApiException` + `GlobalExceptionHandler`로 에러 응답 형식(`{"code","message"}`)을 통일
- 입력 검증(`@Valid`, `@NotNull`, `@Min(1)`, `@Max(1000000)`, `accept-float-as-int: false`) → 400 `INVALID_REQUEST`
- 없는 메뉴 → 404 `MENU_NOT_FOUND`, 잔액 부족 → 409 `INSUFFICIENT_POINT` (잔액은 그대로)
- 주문 시 **포인트 차감과 주문 저장을 한 트랜잭션**(`@Transactional`)으로 묶기
- 데이터 수집 플랫폼 전송 (`MockDataPlatformClient`, 사용자 ID·메뉴 ID·결제 금액)
- 인기 메뉴에 **최근 7일(오늘 포함)** 범위 적용

**여전히 하지 않는 것**
- 동시 요청 보호 (분산 락 / 조건부 UPDATE / 비관적 락)
- 전송 실패 대책 (아웃박스 테이블, 재전송 스케줄러) — 전송을 **트랜잭션 안에서 동기로** 호출합니다
- Redis 집계와 장애 시 폴백

**실행하면 이렇게 됩니다** (포트 8152에서 실측)

| 확인 | 결과 |
|---|---|
| 잔액 부족 (500P로 4,500원 주문) | **409** `INSUFFICIENT_POINT`, 잔액 500 유지, **주문 0건** |
| 없는 메뉴 (`menuId:999`) | **404** `MENU_NOT_FOUND` |
| 음수 충전 / 0원 충전 | **400** `INVALID_REQUEST` (`amount: 1 이상이어야 합니다`) |
| 소수 충전 (`10.5`) | **400** `INVALID_REQUEST` (`요청 본문 형식이 올바르지 않습니다.`) |
| 100만 원 초과 충전 | **400** `INVALID_REQUEST` (`amount: 1000000 이하여야 합니다`) |
| `amount` 누락 | **400** `INVALID_REQUEST` (`amount: 널이어서는 안됩니다`) |
| 포인트 행 없는 사용자 주문 | **409** `INSUFFICIENT_POINT` |
| 데이터 수집 플랫폼 전송 | 주문 11건 → 로그 11건 (`OrderEventPayload(userId=…, menuId=1, amount=4500)`) |
| 10일 전 주문 30건이 있는 메뉴 | 인기 메뉴에서 **빠짐** (최근 7일 범위 적용) |
| **3잔 값(13,500P)으로 동시 10건 주문** | **10건 모두 201**, 주문 10건, **잔액 9,000** — 아직 깨집니다 |
| **100P 충전 100건 동시** | 200 91건 / **500 9건**, **잔액 1,000** (9,100이어야 함) — 아직 깨집니다 |

> 2단계의 두 결과는 **반복해도 같은 값이 나옵니다**(각각 10회·6회 반복해 전부 동일). 1단계는 잔액이 흔들리므로,
> **동시성을 깨뜨려 보이는 시연은 2단계에서** 하는 편이 안전합니다.

> 촬영 포인트: 여기서 동시 요청 명령을 실행해 **직접 깨뜨려 보이는 것**이 3단계의 동기가 됩니다.
> "`@Transactional`을 붙였는데 왜 아직 깨지나?"가 이 단계의 핵심 질문입니다.
> 트랜잭션은 **중간 상태를 감춰 줄 뿐, 같은 행을 동시에 읽는 것을 막지 않습니다.**
> 열 요청이 모두 잔액 13,500을 읽고 "충분하다"를 통과한 뒤 모두 9,000을 덮어씁니다(갱신 분실).
> 깨지는 이유는 코드에 주석으로 표시해 두었습니다 — `OrderService`, `PointService`, `UserPoint`.
>
> 전송 쪽도 짚어 둘 것이 있습니다. 2단계는 전송을 **트랜잭션 안에서 동기로** 호출합니다.
> 플랫폼이 느리면 DB 트랜잭션을 그만큼 오래 잡고, 전송이 실패하면 멀쩡한 결제까지 롤백됩니다.
> 반대로 전송한 뒤 커밋이 실패하면 없는 주문을 보낸 셈이 됩니다. → 3단계

### 동시성 시연 명령 (2단계에서 깨지는 것을 보여 줄 때)

```bash
U=$RANDOM$RANDOM
curl -s -X POST localhost:8080/api/points/charge -H 'Content-Type: application/json' \
  -d "{\"userId\":$U,\"amount\":13500}"            # 아메리카노 3잔 값

for i in $(seq 1 10); do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST localhost:8080/api/orders \
    -H 'Content-Type: application/json' -d "{\"userId\":$U,\"menuId\":1}" &
done; wait

curl -s localhost:8080/api/points/$U                # 2단계: 9000, 3단계: 0
```

### 인기 메뉴 7일 범위 시연 (1단계와 2단계를 비교할 때)

10일 전 주문을 직접 넣어 두고 인기 메뉴를 조회합니다. 1단계는 포함하고, 2·3단계는 제외합니다.

```bash
docker exec solution-mysql-1 mysql -uroot -proot coffee -e \
 "INSERT INTO coffee_order (user_id, menu_id, price, ordered_at)
  SELECT 999000001, 6, 5300, DATE_SUB(NOW(), INTERVAL 10 DAY) FROM menu m1, menu m2 LIMIT 30;"

curl -s localhost:8080/api/menus/popular

# 끝나면 지우기
docker exec solution-mysql-1 mysql -uroot -proot coffee -e \
 "DELETE FROM coffee_order WHERE user_id = 999000001;"
```

## 3단계 — 동시성·전송 실패·집계 (`../solution/`)

2단계에서 남겨 둔 세 가지를 해결합니다.

| 남은 문제 | 3단계의 해법 | 더해지는 코드 |
|---|---|---|
| 같은 사용자의 동시 요청에 잔액이 틀어짐 | `point:{userId}` **분산 락**(Redisson)을 잡고 그 안에서 트랜잭션을 연다. 락 획득 → 트랜잭션 시작 → 커밋 → 락 해제 순서 | `common/lock/DistributedLockExecutor`, `common/config/RedissonConfig` |
| 전송이 트랜잭션 안에 있어 결제와 서로를 끌고 감 | 보낼 내용을 주문과 **같은 트랜잭션에 저장**(아웃박스)하고, **커밋된 뒤** 비동기로 보낸다. 실패하면 `PENDING`으로 남아 스케줄러가 다시 보낸다 | `common/entity/OrderEvent`, `OrderEventRepository`, `OrderEventSender`, `OrderEventRetryScheduler` |
| 조회할 때마다 7일 치 주문을 전부 읽음 | Redis 정렬 집합에 **날짜별로 횟수를 쌓고**(`ZINCRBY`) 조회할 때 7개 키를 합친다. Redis가 멈추면 주문 테이블 집계로 **폴백** | `PopularMenuRanking`, `PopularMenuEventListener`, `PopularMenuService`의 폴백 경로 |

그 밖에 더해지는 것: 락 대기 초과 응답(503 `REQUEST_BUSY`), 중복 전송을 걸러내기 위한 `eventId`, 테스트 25개.

> 촬영 포인트: **왜 `synchronized`로는 안 되는가**를 여기서 설명합니다. 서버를 2대(8080, 8081) 띄우고
> 같은 시나리오를 두 포트에 번갈아 보내면, JVM 안의 락은 다른 서버의 요청을 막지 못한다는 것이 바로 보입니다.
> 평가 기준표 A2는 이 이유로 JVM 락만 쓴 제출을 0점으로 둡니다.
>
> 락의 범위도 짚습니다. 전역 락 하나로도 시나리오는 통과하지만, 서로 상관없는 다른 사용자의 요청까지 줄을 세웁니다(B4).
