# 과제 3. 가상 포트폴리오 수익률 서비스: 평가 기준표

> 튜터용 문서 · **최종본 v1.2** (2026-10-08)
> 튜터가 수강생 제출물을 직접 실행하고 읽어서 채점합니다. 함께 쓰는 자료: 같은 폴더의 `solution/`(정답 서버)

---

## 1. 평가 원칙

1. 모든 항목은 **ID, 판정 질문, 증거 위치, 판정 방법, 수준별 기준**을 가집니다.
2. **명세에 적힌 규칙(A)** 은 튜터가 서버를 띄워 통과/실패를 판정하고, **명세 밖의 빈틈(B)** 은 튜터가 빈틈 상황(I1~I5, 5장)을 **직접 재현해 동작을 관찰**한 뒤 가정 문서와 대조해 판정합니다.
3. **빈틈에는 정답이 없습니다.** 결정의 **내용**이 아니라 **발견, 근거, 일관성, 한계 인식**을 봅니다.
4. 판정은 **증거에 근거**합니다. 파일과 위치, 응답을 적습니다.
5. 애매하면 낮은 수준이 아니라 **"판정 보류"** 로 표시하고 이유를 적습니다.
6. 이 과제의 핵심 능력은 **자율 구현과 명세 해석**입니다. 그래서 명세 해석(B)이 30점, 스스로 설계(C)가 20점입니다.

### 3-2. 평가 순서
1. 가상 시세 서버를 **관리자 기능을 켜서** 실행하고(아래 3-3 명령) `POST /admin/reset`으로 초기화한다. 기본으로 켜져 있는 일시 장애(5%)는 `POST /admin/failure`로 꺼 둔다.
2. 수강생 서버를 기동하고 4장의 **확인 방법**대로 S1~S11을 실행한다. (수강생 저장소의 `requests.http`와 curl, 관리자 API)
3. A 점수를 매긴다.
4. 5장의 I1~I5 상황을 재현해 **관찰 기록**을 남기고, **관찰 기록과 `docs/assumptions.md`를 나란히 놓고** B를 판정한다.
5. 코드를 읽고 C를, 제출물과 문서를 확인하고 D를 판정한다.
6. **치명 오류**를 확인해 감점을 적용한다.
7. 결과를 8-2 양식으로 기록한다.

>
> **정답 서버와 비교하기**: 검색·정렬·필터 결과는 `solution/`을 띄워 같은 요청을 보내 나온 결과와 비교하면 가장 빠릅니다. 두 서버를 함께 띄울 때는 한쪽을 다른 포트로 실행합니다 (예: `SERVER_PORT=8081 ./gradlew bootRun`).

### 3-3. 가상 시세 서버 관리자 기능 (튜터 전용)

가격·환율을 고정하거나 토큰 만료·장애를 **일부러 만들어** 결과를 확실하게 확인할 때 씁니다. 수강생 환경에서는 꺼져 있습니다.

```bash
docker run -p 9091:9091 -e ADMIN_ENABLED=true -e ADMIN_TOKEN=tutor-secret ghcr.io/donghyunkim-hi/portfolio-price-server:1.0.0
```

모든 관리자 요청에 헤더 `X-Admin-Token: tutor-secret`(위 `ADMIN_TOKEN` 값)을 붙입니다. 값이 틀리면 403입니다.

| 기능 | 요청 | 쓰는 곳 |
|---|---|---|
| 가격 고정 | `POST /admin/prices` + `{"prices":{"A001":99999},"freeze":true}` | A3, A4, I1, I2 |
| 환율 고정 | `POST /admin/fx` + `{"rate":1400.00,"freeze":true}` | I3 |
| 토큰 강제 만료 | `POST /admin/tokens/expire` | A6 |
| 장애 모드 | `POST /admin/failure` + `{"mode":"ALWAYS_503","transientFailureRate":0}` (끌 때는 `"mode":"NONE"`) | F2, I4 |
| 초기화 | `POST /admin/reset` — 위 설정과 호출 기록을 모두 원래대로 | 수강생마다 채점 시작 전 |
| 호출 기록 | `GET /admin/requests` — 수강생 서버가 토큰 발급·시세 조회를 언제 했는지 | A5 갱신 간격, A6 토큰 재사용 |

## 4. 영역 A. 명세 정확성 (35점): 실행 확인

**벡터**(검색어, 정렬, 필터 조합)는 튜터가 표에 적힌 개수만큼 골라 **모든 수강생에게 같은 조합**을 씁니다. 기대 결과는 정답 서버(`solution/`)에 같은 요청을 보내 얻습니다. 데이터 정리 관련 기대값은 다음과 같습니다. (데이터를 만들 때 정답 서버와 따로 계산한 값)

| 항목 | 기대값 |
|---|---|
| 원본 행 수 → 유일 상품 수 | 130행 → **120개** |
| 중복 코드 (10개) | A012, A026, A037, A041, A051, A056, A059, A061, A083, A120 |
| 빈 위험등급 (8개) | A025, A038, A057, A074, A108, A113, A115, A117 |
| 유형별 개수 | ETF 55, FUND 40, BOND 25 |
| 정리 후 통화별 개수 | KRW 80, USD 40 |

| ID | 항목 | 배점 | 확인 방법 | 통과 기준 |
|---|---|---|---|---|
| A1-1 (S1) | 상품 검색 | 3 | 코드, 한글 이름, 영문명(대·소문자 섞임) 검색 벡터 6개 | 결과가 기대와 같음 (벡터 통과 비율 × 3, 소수 첫째 자리 반올림) |
| A1-2 (S2) | 상품 정렬 | 2 | 이름, 상장일, 위험등급 × 오름/내림 벡터 6개 | 순서가 기대와 같음 (통과 비율 × 2) |
| A1-3 (S3) | 상품 필터 | 3 | 유형, 통화, 위험등급, 복합(AND) 벡터 8개 | 건수와 항목이 기대와 같음 (통과 비율 × 3) |
| A1-4a (S4) | 유일 상품 수 | 2 | 전체 조회의 `totalElements` | **유일 코드 수**와 같음 (중복 행이 별도 항목으로 나오지 않음) |
| A1-4b (S4) | 통화 표기 통일 | 2 | 전체 상품의 `currency` 값 집합, `currency=USD` 필터 건수 | 값이 `KRW`/`USD`뿐이고, 표기가 다른 행도 필터에 포함되어 **건수가 기대와 같음** |
| A1-4c (S4) | 상장일 정리 | 2 | 전체 상품의 `listedDate` 형식, 상장일 정렬 결과 | 모두 `yyyy-MM-dd`이고 **정렬 순서가 기대와 같음** |
| A2 (S5, S6) | 포트폴리오 CRUD·목록 | 5 | 아래 5가지를 각각 확인 | 항목당 1점 |
| A3 (S7) | 매입 시점 고정 | 4 | 시세 지정 후 갱신을 기다려 생성 → 시세를 바꿔 갱신을 기다림 → 조회 | 매입가와 `totalCost`가 **변하지 않고**, `currentPrice`와 `totalValue`만 갱신 |
| A4 (S8) | 평가 계산 | 4 | 원화 상품 3종, 지정한 시세로 계산 | `totalValue`(1), `profit`(1), `returnRate`(1), **반올림 경계 벡터**(1)가 기대와 같음 |
| A5 (S9) | 시세 갱신 | 4 | (i) 시세 변경 후 **45초 안에** 반영 (ii) 시세 서버 호출 로그의 간격 | (i) 2점, (ii) **호출 간격이 30초 ± 10초로 반복**되면 2점 |
| A6 (S10) | 토큰 | 4 | (i) 토큰을 강제로 만료시킨 뒤 시세를 바꾸고 45초 안에 반영되는가 (ii) 시세 호출 횟수 대비 토큰 발급 횟수 | (i) 2점, (ii) **호출 4회당 토큰 발급이 2회 이하**(재사용)면 2점 |
| **소계** | | **35** | | |

**A2의 5가지 (각 1점)**
1. 생성 → 201, 필수 필드(`id`, `name`, `createdAt`, `holdings`, `summary`) 포함
2. 상세 조회 200, 없는 ID는 404 `PORTFOLIO_NOT_FOUND`
3. 삭제 204, 다시 조회하면 404
4. 입력 오류(이름 없음, 없는 상품 코드, 수량 0, 같은 코드 중복, 종목 21개)가 모두 400
5. 목록의 이름 검색, 정렬(이름·생성일·수익률·평가금액), 페이지 (`totalElements`, `totalPages`)

**S11 (시세 서버 장애)** 는 A 항목이 아니라 **치명 오류 F2**로 판정합니다. 시세 서버를 장애 상태로 만든 뒤 상세·목록 조회가 **5xx를 내면 F2**입니다.

**S9, S10 안정성**: 각각 **2회 반복**해 모두 통과해야 통과로 봅니다. 최대 대기는 시나리오당 60초입니다.

## 5. 영역 B. 명세 해석과 가정 (30점): 읽고 판정

증거는 **`docs/assumptions.md`**, **튜터가 I1~I5를 재현해 남긴 관찰 기록**, 코드입니다.

**목표 빈틈 5개(G1~G5)**: 가이드의 힌트 3에 나온 질문 5개와 같습니다.
G1 구성 변경 시 매입가·수익률, G2 '오늘' 기준, G3 통화 혼재 환산, G4 시세 실패 시 표시, G5 데이터 결함 처리(중복 코드 행 선택, 빈 위험등급)

**관찰 방법 (I1~I5)**: 빈틈에는 정답이 없으므로 통과/실패를 매기지 않고, 수강생 서버가 **실제로 어떻게 동작하는지만 기록**합니다. 시세·환율은 관리자 API로 고정해서 진행합니다.

| ID | 재현 방법 | 기록할 것 |
|---|---|---|
| I1 (G1) 구성 변경 | 시세 고정 → 포트폴리오 생성 → 시세 변경 → 갱신 대기 → `PUT`으로 (a) 종목 추가 (b) 수량 증가 (c) 수량 감소 (d) 종목 삭제를 **각각 별도 포트폴리오에서** 수행 | 각 경우의 `totalCost`, 보유 종목의 `purchasePrice`, `returnRate` |
| I2 (G2) '오늘' 기준 | 시세를 3회 바꾸며 매번 조회 | 각 시점의 `todayProfit`, `totalValue` |
| I3 (G3) 통화 혼재 | 원화 1종 + 달러 1종 포트폴리오 생성 → 환율 변경 → 시세 변경 → 조회 | 환율 변경 전후의 `totalCost`, `totalValue`, `returnRate` |
| I4 (G4) 시세 실패 | (a) 장애 모드(`ALWAYS_503`)로 조회 (b) 시세가 없는 상태에서 생성 시도(가능한 경우) | 응답 상태·본문, 값이 있는지, 오래된 값임을 알리는 표시 필드 |
| I5 (G5) 데이터 결함 | 중복 코드 상품 조회(코드 목록은 4장 기대값 표), 빈 등급 상품 조회(같은 표), 위험등급 정렬·필터 | 어느 행의 값이 나왔는지(이름·상장일·등급), 빈 등급의 위치 |

**판정 질문**: 가정 문서가 **목표 빈틈 5개 중 몇 개**를 식별했는가? (문서의 각 행이 어느 빈틈에 해당하는지 튜터가 매핑)

| 4개 | 6 |
| 3개 | 4 |

### B2. 결정의 합리성과 근거 (8점)
**판정 질문**: 식별한 빈틈마다 **결정, 이유, 다른 선택지**가 있고 이유가 **사용자 입장에서 타당**한가?

**판정 질문**: 문서에 적은 결정이 **관찰한 실제 동작과 일치**하는가?
**증거 위치**: I1~I5 관찰 기록과 가정 문서

| 일치 비율 (식별한 빈틈 중, 관찰 가능한 것 기준) | 점수 |

| 60% 이상 | 4 |

## 6. 영역 C. 설계·구현 (20점): 읽고 판정

### C1. 데이터 모델링 (5점)
**판정 질문**: 상품, 포트폴리오, 보유 종목, 시세를 **역할에 맞게** 모델링하고, **매입 시점의 값(매입가, 필요하면 매입 시점 환율)을 보유 종목에 저장**했는가?
**증거 위치**: 엔티티 또는 스키마

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 5 | 상품·포트폴리오·보유 종목이 분리되고, **매입가가 보유 종목에 저장**되며, 시세는 별도 저장 또는 캐시로 관리 |
| 중 | 3 | 동작하지만 한 엔티티에 몰리거나, 매입가를 저장하지 않고 재계산에 의존 |
| 하 | 1 | 구조가 불명확하거나 요구를 만족하기 어려움 |
| 없음 | 0 | 판정 불가 |

### C2. 외부 연동 구조 (6점)
**판정 질문**: 토큰 관리, 타임아웃, 장애 격리가 설계되어 있는가?
**증거 위치**: 시세 클라이언트 코드

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 6 | **토큰을 보관·재사용**하고 만료 시 **재발급 후 재시도**, **타임아웃 설정**, 실패해도 **호출한 쪽(조회 API)에 영향이 전파되지 않음** |
| 중 | 4 | 재발급은 하지만 재사용이 없거나(매번 발급), 타임아웃이 없음 |
| 하 | 2 | 실패 처리가 거의 없음 (예외가 그대로 전파) |
| 없음 | 0 | 시세 연동 없음 |

### C3. 갱신 구조 (4점)
**판정 질문**: 주기 갱신이 **스케줄러**로 구현되고, 실패해도 이전 값이 유지되며, **동시 접근에 안전**한가?
**증거 위치**: 스케줄러, 시세 저장소

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 4 | 스케줄러 사용, **시작 시 1회 즉시 로드**, 갱신 실패 시 **마지막 성공값 유지**, 읽는 쪽과 쓰는 쪽이 안전하게 분리 (불변 스냅샷 교체, 동기화 컬렉션 등) |
| 중 | 2 | 갱신은 하나 실패 처리나 안전성 중 하나가 부족 |
| 하 | 1 | 조회할 때마다 시세를 호출하는 등 요구(주기 갱신)와 다름 |

### C4. 데이터 정리 방식 (5점)
**판정 질문**: 원본은 두고, **정리 규칙이 명확**하며, 처리 결과를 **알 수 있는가**?
**증거 위치**: 데이터 로딩·정리 코드

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 5 | 정리 규칙(통화 사전, 날짜 형식들, 중복 처리, 빈 값)이 **한곳에 모여 있고**, 처리한 내역(로그나 리포트)을 남김 |
| 중 | 3 | 정리는 되나 규칙이 여러 곳에 흩어지거나 결과를 알 수 없음 |
| 하 | 1 | 일부 결함만 처리 |
| 없음 | 0 | 정리하지 않음 |

### 8-2. 결과 기록 양식

모든 튜터가 **같은 형식**으로 기록합니다. 튜터끼리 결과를 비교하고 기준표를 고칠 때 씁니다.

```json
{
  "studentId": "S-001",
  "evaluator": "튜터 이름",
  "scores": {
    "A": { "A1-1": 3, "A1-2": 2, "A1-3": 2.6, "A1-4a": 0, "A1-4b": 2, "A1-4c": 2, "A2": 4, "A3": 4, "A4": 3, "A5": 2, "A6": 2 },
    "B": { "B1": {"identified": ["G1","G3","G4"], "score": 4, "evidence": "assumptions.md #1,#2,#3"},
           "B2": {"level": "중", "score": 5, "reason": "..."}, "B3": {"matches": [{"gap":"G1","match":true,"evidence":"I1 관찰"}], "score": 6}, "B4": {} },
    "C": { "C1": {"level": "상", "score": 5, "evidence": "Holding.java:15"}, "C2": {}, "C3": {}, "C4": {} },
    "D": { "D1": 5, "D2": {}, "D3": {}, "D4": {} }
  },
  "penalties": [ { "id": "F2", "points": -10, "evidence": "S11: GET /portfolios/1 → 500" } ],
  "hold": [ { "item": "B2", "reason": "판정 보류 사유" } ],
  "total": 0
}
```

- **판정 보류** 항목은 별도 목록에 이유를 남깁니다. 기준표를 개선할 때 가장 중요한 자료입니다.
- **B는 수준(또는 식별한 빈틈)과 근거**(가정 문서의 행, 관찰 기록)를 반드시 적습니다.
