# 과제 3. 가상 포트폴리오 수익률 서비스 평가 기준표

> 평가자용 문서, v1.3 (2026-10-16)
> - 평가자가 지원자 제출물을 직접 실행하고, 코드와 문서를 읽어 채점합니다.
> - 같은 폴더의 `solution/`(정답 서버)을 함께 사용합니다.

---

## 1. 평가 원칙

1. 모든 항목에는 ID, 판정 질문, 증거 위치, 판정 방법, 수준별 기준이 있습니다.
2. 영역에 따라 판정 방법이 다릅니다.
   - 명세에 적힌 규칙(A)은 평가자가 서버를 실행해 통과 여부를 판정합니다.
   - 명세에 없는 빈틈(B)은 평가자가 5장의 빈틈 상황(I1~I5)을 직접 재현해 동작을 관찰하고, 그 결과를 가정 문서와 비교해 판정합니다.
3. 빈틈에는 정답이 없습니다. 어떤 결정을 했는지가 아니라 빈틈을 찾았는지, 근거가 있는지, 문서와 동작이 일치하는지, 한계를 알고 있는지를 봅니다.
4. 판정은 증거를 근거로 합니다. 근거가 된 파일과 위치, 또는 응답 내용을 함께 기록합니다.
5. 판정이 애매하면 낮은 수준을 주지 말고 **판정 보류**로 표시한 뒤 이유를 적습니다.
6. 이 과제는 시작 코드 없이 직접 구현하는 능력과 명세 해석 능력을 봅니다. 그래서 명세 해석(B)에 30점, 설계와 구현(C)에 20점을 배정했습니다.

## 3. 평가 절차

### 3-1. 사전 확인

| 확인 항목 | 기준 | 실패 시 |
|---|---|---|
| 제출 구조 | 루트에 Gradle 프로젝트, `data/products.csv`, `README.md`, `docs/api.md`, `docs/assumptions.md`가 있음 | 빠진 항목을 기록하고 평가 진행 (D1 감점) |
| **데이터 파일** | `data/products.csv`가 원본과 같음. `shasum -a 256 data/products.csv` 결과가 `8058a5978a12cdc19f0b39ad367af376ab631bba48a50a7d97770932a3205e3a`이어야 함 | **치명 오류 F1** |
| 실행 | `./gradlew bootRun`으로 8080 포트에서 실행됨 | **A 영역 0점**. B~D는 코드와 문서로 평가 진행 |
| 시세 서버 연결 | `PRICE_BASE_URL`로 시세 서버 주소를 바꿀 수 있음 | A 감점 |

### 3-2. 평가 순서

1. 가상 시세 서버를 관리자 기능을 켠 상태로 실행합니다. (3-3의 명령 참고)
   - 실행 후 `POST /admin/reset`으로 초기화합니다.
   - 기본으로 켜져 있는 일시 장애(5%)는 `POST /admin/failure`로 꺼 둡니다.
2. 지원자 서버를 실행하고 4장의 확인 방법에 따라 S1~S11을 실행합니다. 지원자 저장소의 `requests.http`, curl, 관리자 API를 함께 사용합니다.
3. A 영역 점수를 매깁니다.
4. 5장의 I1~I5 상황을 재현해 관찰 기록을 남깁니다. 관찰 기록과 `docs/assumptions.md`를 비교해 B 영역을 판정합니다.
5. 코드를 읽고 C, 제출물과 문서를 확인해 D를 판정합니다.
6. 치명 오류가 있는지 확인하고 감점을 적용합니다.
7. 평가 결과를 8-2의 양식으로 기록합니다.

> **정답 서버와 비교하는 방법**
> - 검색, 정렬, 필터 결과는 `solution/`을 실행해 같은 요청을 보내고 결과를 비교하면 가장 빠릅니다.
> - 두 서버를 함께 실행할 때는 한쪽을 다른 포트로 실행합니다. (예: `SERVER_PORT=8081 ./gradlew bootRun`)

### 3-3. 가상 시세 서버 관리자 기능 (평가자 전용)

- 가격과 환율을 고정하거나, 토큰 만료와 장애 상황을 일부러 만들어 결과를 확인할 때 사용합니다.
- 지원자에게 제공하는 환경에서는 관리자 기능이 꺼져 있습니다.

```bash
docker run -p 9091:9091 -e ADMIN_ENABLED=true -e ADMIN_TOKEN=admin-secret ghcr.io/donghyunkim-hi/portfolio-price-server:1.1.0
```

- 모든 관리자 요청에는 헤더 `X-Admin-Token: admin-secret`(위 명령의 `ADMIN_TOKEN` 값)을 붙입니다. 값이 틀리면 403을 응답합니다.

| 기능 | 요청 | 사용하는 항목 |
|---|---|---|
| 가격 고정 | `POST /admin/prices`, 본문 `{"prices":{"A001":99999},"freeze":true}` | A3, A4, I1, I2 |
| 환율 고정 | `POST /admin/fx`, 본문 `{"rate":1400.00,"freeze":true}` | I3 |
| 토큰 강제 만료 | `POST /admin/tokens/expire` | A6 |
| 장애 모드 | `POST /admin/failure`, 본문 `{"mode":"ALWAYS_503","transientFailureRate":0}`<br>끌 때는 `"mode":"NONE"`을 보냅니다. | F2, I4 |
| 초기화 | `POST /admin/reset`<br>위 설정과 호출 기록을 모두 처음 상태로 되돌립니다. | 지원자마다 채점 시작 전 |
| 호출 기록 | `GET /admin/requests`<br>지원자 서버가 토큰 발급과 시세 조회를 언제 요청했는지 보여 줍니다. | A5 갱신 간격, A6 토큰 재사용 |

- 기대 결과는 정답 서버(`solution/`)에 같은 요청을 보내서 얻습니다.
- 데이터 정리와 관련된 기대값은 아래와 같습니다. 데이터를 만들 때 정답 서버와 별도로 계산한 값입니다.

| 원본 행 수와 고유 상품 수 | 130행, 고유 상품 **120개** |
| 중복 코드 (10개) | A012, A026, A037, A041, A051, A056, A059, A061, A083, A120 |
| 위험등급이 비어 있는 상품 (8개) | A025, A038, A057, A074, A108, A113, A115, A117 |

| **소계** | | **35** | | |

**A2에서 확인할 5가지 (각 1점)**

1. 생성 요청에 201을 응답하고, 필수 필드(`id`, `name`, `createdAt`, `holdings`, `summary`)가 있음
2. 상세 조회에 200을 응답하고, 없는 ID는 404 `PORTFOLIO_NOT_FOUND`를 응답함
3. 삭제에 204를 응답하고, 삭제 후 다시 조회하면 404를 응답함
4. 입력 오류(이름 없음, 없는 상품 코드, 수량 0, 같은 코드 중복, 종목 21개)에 모두 400을 응답함
5. 목록 조회에서 이름 검색, 정렬(이름, 생성일, 수익률, 평가금액), 페이지 처리(`totalElements`, `totalPages`)가 동작함

**S11 (시세 서버 장애) 판정**

- S11은 A 영역 항목이 아니라 **치명 오류 F2**로 판정합니다.
- 시세 서버를 장애 상태로 만든 뒤 상세 조회나 목록 조회가 5xx를 응답하면 F2를 적용합니다.

**S9, S10 반복 확인**

- S9와 S10은 각각 **2회 반복**해서 모두 통과해야 통과로 봅니다.
- 시나리오마다 최대 60초까지 기다립니다.

## 5. 영역 B. 명세 해석과 가정 (30점): 읽고 판정

- 증거는 `docs/assumptions.md`, 평가자가 I1~I5를 재현해 남긴 관찰 기록, 코드입니다.

**찾아야 할 빈틈 5개 (G1~G5)**

지원자 README 힌트 4에 나온 질문 5개와 같습니다.

- G1: 포트폴리오 구성을 바꿀 때 매입가와 수익률 처리
- G2: 오늘 손익의 오늘 기준
- G3: 원화와 달러 상품이 섞였을 때의 환산
- G4: 시세를 가져오지 못했을 때 보여 줄 내용
- G5: 데이터 결함 처리 (중복 코드 행 중 어느 행을 쓸지, 비어 있는 위험등급)

**관찰 방법 (I1~I5)**

- 빈틈에는 정답이 없으므로 통과 여부를 매기지 않고, 지원자 서버가 **실제로 어떻게 동작하는지만 기록**합니다.
- 시세와 환율은 관리자 API로 고정한 상태에서 진행합니다.

| ID | 재현 방법 | 기록할 것 |
|---|---|---|
| I1 (G1) 구성 변경 | 시세 고정, 포트폴리오 생성, 시세 변경, 갱신 대기 후 `PUT`으로 (a) 종목 추가 (b) 수량 증가 (c) 수량 감소 (d) 종목 삭제를 **각각 다른 포트폴리오에서** 수행 | 각 경우의 `totalCost`, 보유 종목의 `purchasePrice`, `returnRate` |
| I2 (G2) 오늘 기준 | 시세를 3번 바꾸면서 매번 조회 | 각 시점의 `todayProfit`, `totalValue` |
| I3 (G3) 통화 혼재 | 원화 상품 1종과 달러 상품 1종으로 포트폴리오 생성, 환율 변경, 시세 변경 후 조회 | 환율 변경 전후의 `totalCost`, `totalValue`, `returnRate` |
| I4 (G4) 시세 실패 | (a) 장애 모드(`ALWAYS_503`)에서 조회 (b) 시세가 없는 상태에서 생성 시도 (가능한 경우) | 응답 상태와 본문, 값이 들어 있는지, 오래된 값임을 알리는 필드가 있는지 |
| I5 (G5) 데이터 결함 | 중복 코드 상품 조회, 위험등급이 비어 있는 상품 조회(코드 목록은 4장의 기대값 표 참고), 위험등급 정렬과 필터 | 어느 행의 값(이름, 상장일, 위험등급)이 나왔는지, 비어 있는 위험등급이 어디에 정렬되는지 |

### B1. 빈틈 발견과 기록 (8점)

- **판정 질문**: 가정 문서가 G1~G5 중 몇 개를 찾아냈는가?
  - 문서의 각 행이 어느 빈틈에 해당하는지 평가자가 연결합니다.
- **증거 위치**: `docs/assumptions.md`

| 찾아낸 빈틈 수 | 점수 |
|---|---|
| 5개 | 8 |
| 4개 | 6 |
| 3개 | 4 |
| 2개 | 2 |
| 1개 | 1 |
| 0개 | 0 |

- G1~G5 외에 타당한 다른 빈틈을 찾은 경우, B1 점수를 더 주지는 않고 B2와 B4에서 근거 있는 기록으로 인정합니다.
- 다른 빈틈을 찾았더라도 G1~G5 중 빠진 것을 대신하지는 않습니다.

### B2. 결정의 타당성과 근거 (8점)

- **판정 질문**: 찾아낸 빈틈마다 결정, 이유, 다른 선택지가 있고, 그 이유가 사용자 입장에서 타당한가?
- **증거 위치**: `docs/assumptions.md`의 각 행

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 8 | 찾아낸 빈틈의 **80% 이상**에 결정, 이유, 다른 선택지가 있음. 이유가 타당하고 사용자에게 **오해를 주지 않음** |
| 중 | 5 | 결정과 이유는 있지만 다른 선택지가 없거나, 일부 이유가 약함 (예: 편해서) |
| 하 | 2 | 결정만 있고 이유가 거의 없거나, 결정이 사용자에게 오해를 줌 (예: 시세를 가져오지 못한 사실을 숨기고 최신 값처럼 표시) |
| 없음 | 0 | 가정 문서가 없거나 비어 있음 |
