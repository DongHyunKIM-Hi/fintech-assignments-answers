# 과제 1. 환불 요청 중계 서버 평가 기준표

> 튜터용 문서, v1.3 (2026-10-16)
> - 튜터가 수강생 제출물을 직접 실행하고, 코드와 문서를 읽어 채점합니다.
> - 같은 폴더의 `solution/`(정답 서버)을 함께 사용합니다.

---

## 1. 평가 원칙

1. 모든 항목에는 ID, 판정 질문, 증거 위치, 판정 방법, 수준별 기준이 있습니다.
2. 판정 방법은 영역에 따라 다릅니다.
   - A 영역: 튜터가 서버를 실행하고 요청을 보내 확인합니다.
   - B, C, D 영역: 튜터가 코드와 문서를 읽고 판정합니다.
3. 판정은 증거를 근거로 합니다.
   - 점수를 줄 때 근거가 된 파일과 줄 번호, 또는 응답 내용을 함께 기록합니다.
4. 판정이 애매하면 낮은 수준을 주지 말고 **판정 보류**로 표시한 뒤 이유를 적습니다.
   - 판정 보류 기록은 기준표를 개선할 때 사용합니다.
5. 영역별 판정 기준은 다음과 같습니다.
   - A 영역: 수강생 README에 명시된 요구사항(API 형식, 수치)을 지켰는지 봅니다.
   - B 영역: 내부 설계가 타당한지 봅니다.

## 3. 평가 절차

### 3-1. 사전 확인 (실행 가능 여부)

| 확인 항목 | 기준 | 실패 시 |
|---|---|---|
| 저장소 구조 | 루트에 Gradle 프로젝트, `README.md`, `docs/design.md`가 있음 | 미충족 사유를 기록하고 평가 진행 (D 감점) |
| 실행 | `./gradlew bootRun`으로 8080 포트에서 실행됨 | **A 영역 0점**. B~D는 코드와 문서로 평가 진행 |
| 가상 서버 연결 | `PG_BASE_URL` 환경변수로 결제대행사 주소를 바꿀 수 있음 | A 감점 |

### 3-2. 평가 순서

1. 가상 결제대행사를 관리자 기능을 켠 상태로 실행합니다. (3-3의 명령 참고)
   - 실행 후 `POST /admin/reset`으로 초기화합니다.
2. 수강생 서버를 실행합니다.
3. 4장의 확인 방법에 따라 시나리오 S1~S13을 실행합니다.
   - 수강생 저장소의 `requests.http`와 관리자 API를 함께 사용합니다.
   - `/admin/script`로 응답을 지정하고, `/admin/requests`로 수신 기록을, `/admin/processed`로 처리 기록을 확인합니다.
4. A 영역 점수를 매깁니다.
5. 코드와 DB 구조를 읽고 B, D 영역을 판정합니다.
6. `docs/design.md`를 읽고 C 영역을 판정합니다.
7. 치명 오류가 있는지 확인하고 감점을 적용합니다.
8. 평가 결과를 9장의 양식으로 기록합니다.

> **동시 요청 보내는 방법 (A4, A6)**
> - 셸에서 `for i in $(seq 1 10); do curl -s -X POST ... & done; wait`처럼 `&`를 붙여 요청을 동시에 보낸 뒤 결과를 확인합니다.
>
> **정답 서버와 비교하는 방법**
> - 판정이 애매하면 `solution/`을 같은 방식으로 실행하고 같은 요청을 보내 기대 동작을 확인합니다.

### 3-3. 가상 결제대행사 관리자 기능 (튜터 전용)

- 가상 결제대행사는 기본적으로 무작위로 실패하거나 느리게 응답합니다.
- 관리자 기능을 켜면 원하는 응답을 지정할 수 있어, 재시도, 시간 초과, 이중 환불 상황을 정확하게 재현할 수 있습니다.
- 수강생에게 제공하는 환경에서는 관리자 기능이 꺼져 있습니다.

```bash
docker run -p 9090:9090 -e ADMIN_ENABLED=true ghcr.io/donghyunkim-hi/pg-mock:1.0.0
```

| 기능 | 요청 | 사용하는 항목 |
|---|---|---|
| 초기화 | `POST /admin/reset` | 수강생마다 채점 시작 전 |
| 응답 순서 지정 | `POST /admin/script`, 본문 `{"refundId":"R-1","steps":["FAIL","SUCCESS"]}`<br>`steps`에 `SUCCESS`, `FAIL`, `ERROR`, `SLOW`, `SLOW_BUT_PROCESSED`를 순서대로 지정합니다. 지정한 응답을 모두 사용하면 다시 무작위로 응답합니다. | A8~A10, A12 |
| 수신 기록 | `GET /admin/requests`<br>받은 요청을 순서대로 보여 줍니다. (`refundId`, `orderId`, 받은 시각, 응답한 시각, 결과) | A9 수신 횟수, A11 순서, F2 |
| 처리 기록 | `GET /admin/processed`<br>실제로 환불 처리된 건과 주문별 처리 건수를 보여 줍니다. | A12, F1 |

## 4. 영역 A. 기능 정확성 (35점): 실행 확인

- 시나리오마다 아래 확인 방법대로 요청을 보내고 결과를 확인합니다.
- 통과하면 배점 전체를, 실패하면 0점을 줍니다. (부분 점수 없음)

| ID | 시나리오 | 배점 | 확인 방법 | 통과 기준 |
|---|---|---|---|---|
| A1 (S1) | 정상 접수 | 2 | 유효한 요청 1건 전송 | 202, `status: ACCEPTED`, `duplicate: false`, 응답 시간 **2초 이내** (결제대행사를 기다리지 않음) |
| A2 (S2) | 같은 ID, 같은 내용 | 2 | A1과 같은 요청을 다시 전송 | 200, `duplicate: true`, 목록에 1건만 존재 |
| A3 (S3) | 같은 ID, 다른 내용 | 2 | 같은 ID로 금액만 바꿔 전송 | 409, `code: REFUND_ID_CONFLICT`, 기존 건의 내용이 바뀌지 않음 |
| A4 (S4) | 같은 ID 동시 요청 | 4 | 같은 ID 요청 10건을 동시에 전송 | 신규 접수(`duplicate: false`)가 **정확히 1건**, 나머지 9건은 `duplicate: true`, 목록에 1건 |
| A5 (S5) | 한도 초과 | 2 | 결제 금액 10,000원인 주문에 12,000원 환불 요청 | 422, `REFUND_LIMIT_EXCEEDED`, 조회 시 `REJECTED` 상태와 사유 기록 |
| A6 (S6) | 같은 주문 동시 요청 | 4 | 결제 금액 10,000원인 주문에 4,000원 요청 3건(서로 다른 ID)을 동시에 전송 | `ACCEPTED`(또는 이후 상태) **정확히 2건**, `REJECTED` 1건 |
| A7 (S7) | 입력 오류 | 2 | `refundAmount: 0`, 필수값 누락, 음수 금액을 각각 전송 | 모두 400, `INVALID_REQUEST`, 저장되지 않음 |
| A8 (S8) | 성공 처리 | 2 | `/admin/script`로 `["SUCCESS"]` 지정 후 접수 | 최종 상태 `COMPLETED`, `completedAt` 존재, 가상 서버 수신 1회 |
| A9 (S9) | 실패 후 재시도 | 3 | (a) `["FAIL","SUCCESS"]` 지정: `COMPLETED`, 가상 서버 수신 2회<br>(b) `["FAIL","FAIL","FAIL","FAIL"]` 지정: `FAILED`, 사유 `PG_DECLINED`, 수신 **정확히 4회** | (a)와 (b) 모두 만족 |
| A10 (S10) | 시간 초과 | 3 | `["SLOW","SUCCESS"]` 지정 후 접수 | 60초 안에 종결, `COMPLETED`, 가상 서버 수신 2회 |
| A11 (S11) | 같은 주문 순서 | 2 | 같은 주문에 환불 3건(R-1, R-2, R-3)을 순서대로 전송, 각각 `["SUCCESS"]` 지정 | 가상 서버 수신 기록에서 **R-1 응답 완료 시각 < R-2 수신 시각 < R-2 응답 완료 시각 < R-3 수신 시각** |
| A12 (S12) | 시간 초과 후 실제 처리됨 | 5 | `["SLOW_BUT_PROCESSED","SUCCESS"]` 지정 후 접수 | 60초 안에 종결, 최종 `COMPLETED`, 가상 서버의 `/admin/processed`에서 해당 주문의 처리된 환불이 **정확히 1건**, 다른 `refundId`로 처리된 기록 없음 |
| A13 (S13) | 조회 | 2 | 같은 주문에 환불 25건 생성 후 `page=0,size=10`으로 조회하고, 이어서 `page=2`로 조회 | 첫 페이지 10건, `totalElements: 25`, `totalPages: 3`, **최신순**, 마지막 페이지 5건, 각 항목에 `status`와 `failureReason` 포함 |
| **합계** | | **35** | | |

- A11에서는 다른 주문끼리 서로 기다리지 않는지는 평가하지 않습니다. (설계 자유)
- 한 건이 종결 상태가 될 때까지 최대 90초를 기다립니다. 90초를 넘으면 해당 시나리오는 실패입니다.

## 5. 영역 B. 설계 품질 (35점): 읽고 판정

- 증거는 소스 코드, DB 스키마(엔티티 또는 DDL), 워커 코드입니다.
- 항목마다 아래 기준에 따라 수준을 판정합니다.

### B1. DB 설계 (5점)

- **판정 질문**: 요청 ID의 유일성, 상태, 실패 사유, 재시도 정보를 DB에 저장하도록 설계했는가?
- **증거 위치**: 엔티티 클래스, 스키마

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 5 | `refundId`에 **유일 제약**이 있고, 상태, 실패 사유, 시도 횟수, 재시도 정보(다음 시도 시각 등)를 저장함 |
| 중 | 3 | 유일 제약은 있지만 재시도 정보나 실패 사유 저장이 부족함 |
| 하 | 1 | 유일 제약이 없거나, 필수 정보가 여러 개 빠짐 |
| 없음 | 0 | 판정할 DB 설계가 없음 |

### B2. 접수와 처리의 분리 (6점)

- **판정 질문**: 접수 API가 결제대행사 응답을 기다리지 않고, 처리는 별도 흐름(워커)에서 하는가?
- **증거 위치**: 접수 API 코드 경로, 워커 코드

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 6 | 접수 API는 저장 후 바로 응답하고 처리는 워커가 담당함. **접수 코드 경로에 결제대행사 호출이 없음** |
| 중 | 4 | 분리했지만 일부 경로(재처리, 특정 조건)에서 접수 중에 결제대행사를 호출함 |
| 하 | 0 | 접수 API가 결제대행사를 동기로 호출함 (**치명 오류**, 8장 참고) |

### B3. 재시도 설계 (7점)

- **판정 질문**: 재시도 횟수, 간격, 종료 조건, 최종 실패 처리가 명확하고, 재시도할 때 같은 `refundId`를 사용하는가?
- **증거 위치**: 워커 코드, 재시도 관련 설정

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 7 | 최대 시도 횟수와 종료 조건이 코드에 명확함. 재시도 사이에 간격을 둠. 재시도할 때 **같은 `refundId`를 사용**함. 최종 실패 시 `FAILED` 상태와 사유를 기록함 |
| 중 | 5 | 재시도는 하지만 다음 중 하나가 부족함: 간격 없음, 종료 조건 불명확, 최종 실패 사유 미기록 |
| 하 | 3 | 재시도는 하지만 횟수 제한이 없거나(무한 재시도) 결함이 여러 개 있음 |
| 없음 | 0 | 재시도가 없음 |

### B4. 중복 요청과 동시 요청 방지 방식 (7점)

- **판정 질문**: 같은 ID의 동시 요청과 같은 주문의 합계 경합을 올바른 방식으로 막았는가?
  - A4, A6 통과 여부와 별개로, 사용한 방식이 타당한지 봅니다.
- **증거 위치**: 접수 로직, 저장 시 사용한 제약과 잠금

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 7 | ID 중복은 **DB 유일 제약** 등 마지막 방어 수단으로 막고, 한도 경합은 **조회와 저장을 하나의 단위로 처리**(주문 단위 잠금, 락 등)해서 막음. 두 방식이 일관됨 |
| 중 | 5 | 둘 중 하나만 올바름 (예: ID 중복은 제약으로 막았지만, 한도는 조회 후 저장하는 방식만 사용) |
| 하 | 3 | 애플리케이션 메모리에서 단순히 확인하는 방식처럼 **동시 요청에서 깨질 수 있는** 방식 |
| 없음 | 0 | 중복 방지가 없음 |

### B5. 시간 초과와 이중 환불 대비 (5점)

- **판정 질문**: 응답 대기 시간을 설정했고, 시간 초과 후 재시도가 이중 환불을 만들지 않도록 설계했는가?
- **증거 위치**: 결제대행사 호출 코드, 재시도 코드

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 5 | 응답 대기 시간을 설정함. 재시도에 **같은 ID를 재사용**하거나, 재시도 전에 **결과 조회로 처리 여부를 확인**함. 그 이유를 설계 문서에 설명함 |
| 중 | 3 | 응답 대기 시간은 있지만, 이중 환불을 고려한 흔적이 코드에 없음 |
| 하 | 0 | 응답 대기 시간 설정이 없음 (기본값에 의존해 무한히 기다릴 수 있음) |

### B6. 순서 처리 (5점)

- **판정 질문**: 같은 주문은 접수 순서대로 한 건씩, 다른 주문은 병렬로 처리하도록 설계했는가?
- **증거 위치**: 워커가 처리할 건을 고르는 로직

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 5 | 주문마다 가장 오래된 건만 골라 처리함. 서로 다른 주문은 병렬로 처리할 수 있음 |
| 중 | 3 | 순서는 지키지만 전체를 한 건씩만 처리함 (처리량을 고려하지 않음) |
| 하 | 0 | 순서를 고려하지 않고 병렬로 처리함 |

## 6. 영역 C. 설계 문서 (15점): 읽고 판정

- 증거는 `docs/design.md`입니다.

### C1. 필수 항목 작성 (5점)

- **판정 질문**: 5개 제목(상태 정의, 재시도 방식, 중복 방지 방법, 시간 초과 처리, 순서 처리 방식)이 있고, 각 제목 아래에 내용이 작성되어 있는가?

| 점수 | 기준 |
|---|---|
| 항목당 1점 | 제목 아래에 구체적인 내용(실제 수치, 방법 등)이 1문장 이상 있음 |
| 0점 | 제목만 있거나, 적절히 처리함처럼 구체적인 내용이 없음 |

### C2. 선택의 근거 (6점)

- **판정 질문**: 각 결정에 왜 그렇게 했는지 이유가 적혀 있는가?

## 8. 치명 오류와 감점

- 아래 오류는 영역 점수와 별개로 감점합니다.
- 감점을 적용해도 영역 점수는 0점 아래로 내려가지 않습니다.

| ID | 치명 오류 | 감점 | 확인 방법 |
|---|---|---|---|
| F1 | **이중 환불 발생** (한 환불이 서로 다른 ID로 두 번 이상 처리됨) | −10 | A9, A12 확인 결과와 `/admin/processed` |
| F2 | **재시도할 때 `refundId`가 바뀜** | −10 | `/admin/requests`에서 같은 환불이 다른 ID로 수신됨 |
| F3 | **접수 API가 결제대행사 응답을 기다림** | −10 | A1 응답 시간, 접수 코드 경로 (B2 하와 함께 적용) |

- F1~F3이 여러 개 해당해도 중복 적용하지 않고, 가장 큰 감점 하나만 적용합니다.

## 9. 평가 결과 기록 양식

- 모든 튜터가 같은 형식으로 기록합니다.
- 튜터끼리 결과를 비교하거나 기준표를 고칠 때 사용합니다.

```json
{
  "studentId": "S-001",
  "evaluator": "튜터 이름",
  "scores": {
    "A": { "A1": 2, "A2": 2, "A3": 0, "A4": 4, "A5": 2, "A6": 0, "A7": 2, "A8": 2, "A9": 3, "A10": 3, "A11": 2, "A12": 5, "A13": 2 },
    "B": { "B1": {"level": "상", "score": 5, "evidence": "Refund.java:12 unique=true", "reason": "..."},
           "B2": {"level": "상", "score": 6, "evidence": "RefundService.java:40-55", "reason": "..."},
           "B3": {}, "B4": {}, "B5": {}, "B6": {} },
    "C": { "C1": {}, "C2": {}, "C3": {} },
    "D": { "D1": {}, "D2": {}, "D3": {}, "D4": {} }
  },
  "penalties": [ { "id": "F1", "points": -10, "evidence": "..." } ],
  "hold": [ { "item": "B4", "reason": "판정 보류 사유" } ],

```

- 판정 보류 항목은 `hold` 목록에 이유와 함께 남깁니다. 기준표를 개선할 때 가장 중요한 자료입니다.
- 평가자는 수준(상, 중, 하)과 근거(파일과 위치, 또는 응답 내용)를 반드시 적습니다.
