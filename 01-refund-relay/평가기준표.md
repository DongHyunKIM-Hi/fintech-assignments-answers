# 과제 1. 환불 요청 중계 서버: 평가 기준표

> 튜터용 문서 · **최종본 v1.2** (2026-10-08)
> 튜터가 수강생 제출물을 직접 실행하고 읽어서 채점합니다. 함께 쓰는 자료: 같은 폴더의 `solution/`(정답 서버)

---

## 1. 평가 원칙

1. **모든 항목은 ID, 판정 질문, 증거 위치, 판정 방법, 수준별 기준**을 가집니다.
2. **실행으로 판정 가능한 것(A, E)은 튜터가 서버를 띄워 요청을 보내 확인**하고, **읽고 판단하는 것(B, C, D)은 튜터가 코드와 문서를 읽고** 판정합니다.
3. 판정은 **증거에 근거**합니다. 점수를 줄 때 어느 파일 몇 번째 줄, 어느 응답인지 적습니다.
4. 애매하면 **낮은 수준**이 아니라 **"판정 보류"** 로 표시하고 이유를 적습니다. (기준표 개선의 재료가 됩니다)
5. **수강생 가이드에 적힌 약속(API 형식, 수치)을 어겼는지**가 A의 기준이고, **내부 설계의 타당성**이 B의 기준입니다.

## 3. 평가 절차

### 3-1. 사전 확인 (실행 가능 여부)
| 확인 | 기준 | 실패 시 |
|---|---|---|
| 저장소 구조 | 루트에 Gradle 프로젝트, `README.md`, `docs/design.md` | 구조 미충족 사유 기록 후 평가 진행 (D 감점) |
| 실행 | `./gradlew bootRun`으로 8080 포트에서 기동 | **A 영역 0점**, B~D는 코드·문서 기준으로 진행 |
| 가상 서버 연결 | `PG_BASE_URL` 환경변수로 주소 변경 가능 | A 감점 |

### 3-2. 평가 순서
1. 가상 결제대행사를 **관리자 기능을 켜서** 실행하고(아래 3-3 명령) `POST /admin/reset`으로 초기화한다.
2. 수강생 서버를 기동한다.
3. 4장·8장의 **확인 방법**대로 시나리오 S1~S13을 실행한다. 수강생 저장소의 `requests.http`와 관리자 API(`/admin/script`로 응답 지정, `/admin/requests`로 수신 로그, `/admin/processed`로 처리 기록)를 함께 쓴다.
4. A와 E 점수를 매긴다.
5. 코드와 DB 구조를 읽고 B, D를 판정한다.
6. `docs/design.md`를 읽고 C를 판정한다.
7. **치명 오류** 여부를 확인해 감점을 적용한다.
8. 평가 결과를 10장 양식으로 기록한다.

> **동시 요청 보내기 (A4, A6)**: 셸에서 `for i in $(seq 1 10); do curl -s -X POST ... & done; wait`처럼 `&`로 동시에 보낸 뒤 결과를 확인합니다.
>
> **정답 서버와 비교하기**: 판단이 애매하면 `solution/`을 같은 방식으로 띄워 같은 요청을 보내 보면 기대 동작을 바로 확인할 수 있습니다.

### 3-3. 가상 결제대행사 관리자 기능 (튜터 전용)

가상 결제대행사는 원래 무작위로 실패하거나 느려집니다. 관리자 기능을 켜면 원하는 상황을 **일부러 만들 수 있어** 재시도·시간 초과·이중 환불을 확실하게 확인할 수 있습니다. 수강생 환경에서는 꺼져 있습니다.

```bash
docker run -p 9090:9090 -e ADMIN_ENABLED=true ghcr.io/donghyunkim-hi/pg-mock:1.0.0
```

| 기능 | 요청 | 쓰는 곳 |
|---|---|---|
| 초기화 | `POST /admin/reset` | 수강생마다 채점 시작 전 |
| 응답 순서 지정 | `POST /admin/script` + `{"refundId":"R-1","steps":["FAIL","SUCCESS"]}` — `steps`에 `SUCCESS`, `FAIL`, `ERROR`, `SLOW`, `SLOW_BUT_PROCESSED`를 순서대로 지정. 지정한 응답을 다 쓰면 다시 무작위 | A8~A10, E1 |
| 수신 기록 | `GET /admin/requests` — 받은 요청을 순서대로 (`refundId`, `orderId`, 받은 시각, 응답한 시각, 결과) | A9 수신 횟수, A11 순서, F2 |
| 처리 기록 | `GET /admin/processed` — 실제로 환불 처리된 건과 주문별 처리 건수 | E1, F1 |

## 4. 영역 A. 기능 정확성 (35점): 실행 확인

시나리오마다 튜터가 아래 **확인 방법**대로 요청을 보내고 결과를 확인합니다. 통과하면 만점, 실패하면 0점 (부분 점수 없음).

| ID | 시나리오 | 배점 | 확인 방법 | 통과 기준 |
|---|---|---|---|---|
| A1 (S1) | 정상 접수 | 3 | 유효한 요청 1건 전송 | 202, `status: ACCEPTED`, `duplicate: false`, 응답 시간이 **2초 이내** (결제대행사를 기다리지 않음) |
| A2 (S2) | 같은 ID·같은 내용 | 3 | A1과 같은 요청을 다시 전송 | 200, `duplicate: true`, 목록에 1건만 존재 |
| A3 (S3) | 같은 ID·다른 내용 | 2 | 같은 ID로 금액만 바꿔 전송 | 409, `code: REFUND_ID_CONFLICT`, 기존 건의 내용이 변하지 않음 |
| A4 (S4) | 같은 ID 동시 요청 | 4 | 같은 ID 요청 10건을 동시에 전송 | 신규 접수(`duplicate: false`)가 **정확히 1건**, 나머지 9건은 `duplicate: true`, 목록에 1건 |
| A5 (S5) | 한도 초과 | 3 | 결제 10,000원 주문에 12,000원 환불 요청 | 422, `REFUND_LIMIT_EXCEEDED`, 조회 시 `REJECTED` + 사유 기록 |
| A6 (S6) | 같은 주문 동시 요청 | 4 | 결제 10,000원 주문에 4,000원 요청 3건(서로 다른 ID)을 동시에 전송 | `ACCEPTED`(또는 이후 상태) **정확히 2건**, `REJECTED` 1건 |
| A7 (S7) | 입력 오류 | 2 | `refundAmount: 0`, 필수값 누락, 음수 각각 전송 | 모두 400, `INVALID_REQUEST`, 저장되지 않음 |
| A8 (S8) | 성공 처리 | 3 | `/admin/script`로 `["SUCCESS"]` 지정 후 접수 | 종결 상태가 `COMPLETED`, `completedAt` 존재, 가상 서버 수신 1회 |
| A9 (S9) | 실패 후 재시도 | 3 | (a) `["FAIL","SUCCESS"]` → `COMPLETED`, 가상 서버 수신 2회. (b) `["FAIL","FAIL","FAIL","FAIL"]` → `FAILED`, 사유 `PG_DECLINED`, 수신 **정확히 4회** | (a), (b) 모두 만족 |
| A10 (S10) | 시간 초과 | 3 | `["SLOW","SUCCESS"]` 지정 후 접수 | 60초 안에 종결, `COMPLETED`, 가상 서버 수신 2회 |
| A11 (S11) | 같은 주문 순서 | 2 | 같은 주문에 환불 3건(R-1, R-2, R-3)을 순서대로 전송, 각각 `["SUCCESS"]` | 가상 서버 수신 로그에서 **R-1의 응답 완료 시각 < R-2의 수신 시각 < R-2의 응답 완료 시각 < R-3의 수신 시각** |
| A13 (S13) | 조회 | 3 | 같은 주문에 환불 25건 생성 후 `page=0,size=10` 조회, 이어서 `page=2` 조회 | 첫 페이지 10건·`totalElements: 25`·`totalPages: 3`, **최신순**, 마지막 페이지 5건, 각 항목에 `status`·`failureReason` 포함 |
| **합계** | | **35** | | |

- A11은 다른 주문끼리 서로 기다리지 않는지는 **평가하지 않음** (설계 자유).
- 종결 상태를 기다리는 최대 시간은 **건당 90초**입니다. 넘으면 해당 시나리오는 실패입니다.

## 5. 영역 B. 설계 품질 (35점): 읽고 판정

증거는 **소스 코드, DB 스키마(엔티티 또는 DDL), 워커 코드**입니다. 아래 기준의 **수준**을 판정합니다.

### B1. DB 설계 (5점)
**판정 질문**: 요청 ID의 유일성, 상태, 실패 사유, 재시도 정보를 DB에 저장하도록 설계했는가?
**증거 위치**: 엔티티 클래스, 스키마

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 5 | `refundId`에 **유일 제약**이 있고, 상태·실패 사유·시도 횟수·(다음 시도 시각 등 재시도 정보)가 저장됨 |
| 중 | 3 | 유일 제약은 있으나 재시도 정보나 실패 사유 저장이 부족 |
| 하 | 1 | 유일 제약이 없거나 필수 정보 저장이 다수 빠짐 |
| 없음 | 0 | 판정할 DB 설계가 없음 |

### B2. 접수와 처리의 분리 (6점)
**판정 질문**: 접수 API가 결제대행사 응답을 기다리지 않고, 처리는 별도 흐름(워커)에서 하는가?
**증거 위치**: 접수 API 코드 경로, 워커 코드

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 6 | 접수는 저장 후 즉시 응답하고 처리는 워커가 담당. **접수 코드 경로에서 결제대행사 호출이 없음** |
| 중 | 4 | 분리했으나 일부 경로(재처리, 특정 조건)에서 접수 중에 결제대행사를 호출 |
| 하 | 0 | 접수 API가 결제대행사를 동기로 호출 (**치명 오류**, 9장 참조) |

### B3. 재시도 설계 (7점)
**판정 질문**: 재시도의 횟수·간격·종료 조건·최종 실패 처리가 명확하고, 재시도 때 같은 `refundId`를 쓰는가?
**증거 위치**: 워커 코드, 재시도 관련 설정

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 7 | 최대 시도 횟수와 종료 조건이 코드에 명확하고, 간격을 둠, 재시도 때 **같은 `refundId` 사용**, 최종 실패 시 `FAILED`와 사유 기록 |
| 중 | 5 | 재시도는 하나 다음 중 하나가 부족: 간격 없음, 종료 조건이 불명확, 최종 실패 사유 미기록 |
| 하 | 3 | 재시도가 있으나 횟수 제한이 없거나(무한) 여러 결함이 있음 |
| 없음 | 0 | 재시도가 없음 |

### B4. 중복·동시 요청 방지 방식 (7점)
**판정 질문**: 같은 ID의 동시 요청과 같은 주문의 합계 경합을 **올바른 메커니즘**으로 막았는가? (A4, A6 통과 여부와 별개로 방식의 타당성을 봄)
**증거 위치**: 접수 로직, 저장 시 제약과 잠금

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 7 | ID 중복은 **DB 유일 제약 등 최종 방어선**으로, 한도 경합은 **조회와 저장의 원자성**(주문 단위 잠금, 락 등)으로 처리. 방식이 일관됨 |
| 중 | 5 | 한쪽만 올바름 (예: ID는 제약으로 막았으나 한도는 "조회 후 저장"만 사용) |
| 하 | 3 | 애플리케이션 메모리의 단순 체크 등 **동시 요청에서 깨질 수 있는** 방식 |
| 없음 | 0 | 중복 방지가 없음 |

### B5. 시간 초과·이중 환불 대비 (5점)
**판정 질문**: 응답 대기 시간이 있고, 시간 초과 후 재시도가 이중 환불을 만들지 않게 설계했는가?
**증거 위치**: 결제대행사 호출 코드, 재시도 코드

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 5 | 응답 대기 시간을 설정했고, 재시도에 **같은 ID를 재사용**하거나 재시도 전에 **결과 조회로 확인**함. 이유를 설계 문서에서 설명 |
| 중 | 3 | 대기 시간은 있으나 이중 환불에 대한 고려가 코드에 보이지 않음 |
| 하 | 0 | 대기 시간 설정이 없음 (기본값에 의존해 무한 대기 가능) |

### B6. 순서 처리 (5점)
**판정 질문**: 같은 주문은 접수 순서대로 하나씩, 다른 주문은 병렬로 처리하도록 설계했는가?
**증거 위치**: 워커의 처리 대상 선택 로직

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 5 | 주문 단위로 가장 오래된 건만 선택해 처리. 주문 간에는 병렬 처리 가능 |
| 중 | 3 | 순서는 지키지만 전체를 하나씩만 처리 (처리량을 고려하지 않음) |
| 하 | 0 | 순서를 고려하지 않고 병렬 처리 |

## 6. 영역 C. 설계 문서 (15점): 읽고 판정

증거는 `docs/design.md`입니다.

### C1. 필수 항목 충족 (5점)
**판정 질문**: 5개 제목(상태 정의, 재시도 방식, 중복 방지 방법, 시간 초과 처리, 순서 처리 방식)이 있고 각각 내용이 채워져 있는가?

| 점수 | 기준 |
|---|---|
| 항목당 1점 | 해당 제목 아래에 **구체적인 내용**(예: 실제 숫자, 방법)이 1문장 이상 있음. 제목만 있거나 "적절히 처리"처럼 내용이 없으면 0점 |

### C2. 선택의 근거 (6점)
**판정 질문**: 각 결정에 **왜 그렇게 했는지** 이유가 있는가?

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 6 | 5개 항목 중 **4개 이상**에서 이유가 있고, 이유가 실제 설계(코드)와 일치 |
| 중 | 4 | 2~3개 항목에서 이유가 있음 |
| 하 | 2 | 이유가 1개 항목에만 있거나 코드와 맞지 않음 |
| 없음 | 0 | 이유가 없고 설명만 있음 |

### C3. 트레이드오프와 한계 인식 (4점)
**판정 질문**: 다른 선택지와 비교하거나, 자신의 설계의 한계·개선점을 인식했는가?

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 4 | **2개 이상의 결정**에서 다른 선택지와 비교하거나, 한계와 개선 방향을 구체적으로 서술 |
| 중 | 2 | 1개 결정에서만 언급 |
| 없음 | 0 | 언급 없음 |

## 7. 영역 D. 코드 품질 (10점)

### D1. 구조 분리 (3점)
| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 3 | 접수(컨트롤러), 도메인/서비스, 저장소, 워커, 외부 연동이 **역할별로 분리**됨 |

## 9. 치명 오류와 감점

아래 오류는 해당 영역 점수와 별개로 **감점**합니다. (영역 점수는 0 미만이 되지 않음)

| ID | 치명 오류 | 감점 | 확인 방법 |
|---|---|---|---|
| F1 | **이중 환불 발생** (한 환불이 서로 다른 ID로 두 번 이상 처리됨) | −10 | E1, A9 확인 결과와 `/admin/processed` |
| F2 | **재시도 때 `refundId`가 바뀜** | −10 | `/admin/requests`에서 같은 환불에 다른 ID가 수신됨 |
| F3 | **접수 API가 결제대행사 응답을 기다림** | −10 | A1 응답 시간, 접수 코드 경로 (B2 하와 함께 적용) |

## 10. 평가 결과 기록 양식

모든 튜터가 **같은 형식**으로 기록합니다. 튜터끼리 결과를 비교하고 기준표를 고칠 때 씁니다.

```json
{
  "studentId": "S-001",
  "evaluator": "튜터 이름",
  "scores": {
    "A": { "A1": 3, "A2": 3, "A3": 0, "A4": 4, "A5": 3, "A6": 0, "A7": 2, "A8": 3, "A9": 3, "A10": 3, "A11": 2, "A13": 3 },
    "B": { "B1": {"level": "상", "score": 5, "evidence": "Refund.java:12 unique=true", "reason": "..."},
           "B2": {"level": "상", "score": 6, "evidence": "RefundService.java:40-55", "reason": "..."},
           "B3": {}, "B4": {}, "B5": {}, "B6": {} },
    "C": { "C1": {}, "C2": {}, "C3": {} },
    "D": { "D1": {}, "D2": {}, "D3": {}, "D4": {} },
    "E": { "E1": 5 }
  },
  "penalties": [ { "id": "F1", "points": -10, "evidence": "..." } ],
```

- **판정 보류** 항목은 별도 목록에 이유를 남깁니다. 기준표를 개선할 때 가장 중요한 자료입니다.
