# 2단계 — 예외 처리와 시나리오

과제 1(환불 요청 중계 서버) 정답 코드를 세 단계로 나눈 것 중 두 번째입니다.
1단계의 정상 경로 위에 **입력 검증, 에러 응답, 재시도, 시간 초과**를 얹습니다.

## 추가하는 것

| 영역 | 내용 |
|---|---|
| 접수 | 입력 검증 → 400 `INVALID_REQUEST` (S7) |
| 접수 | 같은 환불 ID + 같은 내용 → 200 `duplicate: true` (S2) |
| 접수 | 같은 환불 ID + 다른 내용 → 409 `REFUND_ID_CONFLICT` (S3) |
| 접수 | 한도 초과 → 422 `REFUND_LIMIT_EXCEEDED`, `REJECTED`로 저장 (S5) |
| 조회 | 없는 환불 ID → 404 `REFUND_NOT_FOUND`, 주문별 목록 조회(최신순, 페이지 나누기) (S13) |
| 처리 | 응답 대기 시간 5초, 초과하면 `PG_TIMEOUT`으로 보고 **같은 `refundId`로** 재시도 (S10, S12) |
| 처리 | 최초 시도 포함 최대 4번, 간격 0.5초 → 1초 → 2초. 끝까지 실패하면 `FAILED` + 실패 사유 (S9) |
| 처리 | 스레드 풀 도입. 느린 건 하나가 나머지 전부를 막지 않습니다 |

## 여전히 하지 않는 것 — 3단계 몫

| 항목 | 지금 벌어지는 일 |
|---|---|
| 동시 요청 안전성 (접수) | 같은 환불 ID가 동시에 들어오면 **2건이 저장**됩니다 (S4 위반). 같은 주문에 동시에 들어오면 **한도를 넘겨 접수**됩니다 (S6 위반) |
| 같은 주문 순서 처리 | 같은 주문의 환불 두 건이 **동시에** 결제대행사로 나갑니다 (S11 위반) |

깨지는 자리는 코드에 주석으로 표시해 두었습니다.
- `RefundService.accept()` — "조회와 저장 사이", "합계와 저장 사이"
- `RefundWorker.tick()` — 막는 단위가 "건"이라 같은 주문이 나란히 나가는 자리

## 실행

```bash
# 가상 결제대행사
docker run -p 9090:9090 ghcr.io/donghyunkim-hi/pg-mock:1.1.1

# 환불 서버
./gradlew bootRun
```

- 결제대행사 주소는 환경변수 `PG_BASE_URL`로 바꿀 수 있습니다. (기본값 `http://localhost:9090`)
- 단계별로 실제 확인한 결과는 `../README.md`에 있습니다.
