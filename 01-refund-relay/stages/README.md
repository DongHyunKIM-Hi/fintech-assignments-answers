# 단계별 구현 — 환불 요청 중계 서버

해설 영상에서 **한 번에 완성하지 않고 세 단계로 나눠** 만들어 가기 위한 코드입니다.
각 단계는 그대로 실행되는 프로젝트이고, 다음 단계는 앞 단계에 얹는 구조입니다.

| 단계 | 폴더 | 한 문장 |
|---|---|---|
| 1 | `step1-정상경로/` | 접수 API와 워커가 분리되어 돌아가는지만 확인합니다. 검증도 재시도도 없습니다. |
| 2 | `step2-예외처리/` | 입력 검증·에러 응답·재시도·시간 초과를 채웁니다. 아직 동시성과 순서는 없습니다. |
| 3 | `../solution/` | 락의 범위를 설계해 동시 요청과 같은 주문의 순서를 해결합니다. |

실행은 어느 폴더에서든 같습니다.

```bash
docker run -p 9090:9090 ghcr.io/donghyunkim-hi/pg-mock:1.0.0   # 가상 결제대행사
./gradlew bootRun                                               # 환불 서버
```

---

## 1단계 — 정상 경로

**만드는 것**: 접수 API(저장 후 바로 202), 단건 조회, 처리 워커(0.3초마다 `ACCEPTED` 건을 꺼내 결제대행사를 **한 번** 호출).

**일부러 하지 않는 것**: 입력 검증, 중복·충돌·한도 판단, 조회 404와 목록, 응답 대기 시간, 재시도, 순서와 동시성.

**실행하면 이렇게 됩니다** (실측)

| 확인 | 결과 |
|---|---|
| 정상 접수 | **202**를 0.10초에 응답(결제대행사를 기다리지 않음) → 1.4초 뒤 `COMPLETED`, `attemptCount: 1` |
| 같은 환불 ID로 다시 요청 | **202**가 한 번 더 나가고 **DB에 2건** 저장 → 그 뒤 단건 조회가 **500** |
| 같은 환불 ID, 다른 금액 | **202** (409여야 함 → 2단계) |
| 한도 초과 (10,000원에 8,000 + 8,000) | 둘 다 **202**, 둘 다 `COMPLETED` — **16,000원 환불** (422여야 함 → 2단계) |
| `refundAmount: 0` | **202**로 접수 → 결제대행사가 거절 → `FAILED` (400이어야 함 → 2단계) |
| `refundId` 누락 | **500** (DB not-null 위반) |
| 없는 환불 ID 조회 | **200**, 빈 본문 (404여야 함 → 2단계) |
| 목록 조회 | **405** — API 자체가 없음 (→ 2단계) |
| 결제대행사가 `FAIL` 응답 | `attemptCount: 1`로 바로 `FAILED` — 재시도 없음 (→ 2단계) |
| 결제대행사 응답이 12초 걸림 | 타임아웃이 없어 **12초를 그대로 기다린 뒤** `FAILED`. 그동안 **다른 주문**까지 13초 밀림 (→ 2단계) |

> 촬영 포인트: "워커가 돌고 202가 나간다"까지는 금방 됩니다. 그 상태에서 같은 요청을 두 번 보내고
> 금액을 초과시켜 보면, **돌아가는 것과 요구사항을 만족하는 것이 다르다**는 게 한 번에 보입니다.

## 2단계 — 예외 처리와 시나리오

**추가하는 것**
- `ApiExceptionHandler`로 에러 응답 형식(`{"code","message","refundId"}`)을 통일, 검증 위반은 400 `INVALID_REQUEST`
- 접수: 같은 ID·같은 내용 → 200 `duplicate: true` / 같은 ID·다른 내용 → 409 / 한도 초과 → 422 + `REJECTED` 저장
- 조회: 없는 ID → 404 `REFUND_NOT_FOUND`, 주문별 목록(최신순, `page`/`size`/`totalElements`/`totalPages`)
- 처리: 응답 대기 5초 → `PG_TIMEOUT`, **같은 `refundId`로** 최대 4번 시도(간격 0.5초 → 1초 → 2초), 실패 사유 기록
- 처리: 스레드 풀 도입(`pool-size: 8`). 느린 건 하나가 나머지를 막지 않음

**여전히 하지 않는 것**: 접수의 동시 요청 안전성(주문 단위 락, DB 유일 제약), 같은 주문의 순서 보장.

**실행하면 이렇게 됩니다** (실측)

| 확인 | 결과 |
|---|---|
| 정상 접수 | 202를 0.07초에 응답 → `COMPLETED`, `attemptCount: 1` |
| 같은 ID, 같은 내용 (사유만 다름) | **200** `{"duplicate":true,"status":"COMPLETED"}` |
| 같은 ID, 다른 금액 | **409** `REFUND_ID_CONFLICT` |
| 한도 초과 | **422** `REFUND_LIMIT_EXCEEDED` + `REJECTED`로 저장 → 같은 내용 재요청은 **200** `REJECTED, duplicate:true` |
| `refundAmount: 0` / 필수값 누락 / `paidAmount: 10.5` | 모두 **400** `INVALID_REQUEST` |
| 없는 ID 조회 / `orderId` 없는 목록 조회 | **404** `REFUND_NOT_FOUND` / **400** `INVALID_REQUEST` |
| 재시도 (`FAIL` → `FAIL` → `SUCCESS`) | `attemptCount: 3`, `COMPLETED` (3.6초) |
| 최종 실패 (`FAIL` 4회) | `FAILED` + `PG_DECLINED`, `attemptCount: 4` (7.7초) |
| 5xx 4회 | `FAILED` + `PG_ERROR`, `attemptCount: 4` (9.1초) |
| 12초 지연 4회 | 5초마다 끊고 재시도 → `FAILED` + `PG_TIMEOUT`, `attemptCount: 4` (23.7초, 60초 제한 안) |
| 지연됐지만 실제로는 처리됨 (S12) | 5초에 시간 초과 → 같은 ID로 재시도 → `attemptCount: 2`로 `COMPLETED`, 결제대행사 처리 기록 **1건** |
| 느린 건이 있을 때 다른 주문 | 0.9초에 `COMPLETED` — 1단계에서 13초 밀리던 것이 해결됨 |
| **같은 환불 ID로 동시 5건** | **5건 모두 202, DB에 5건 저장** → 단건 조회 **500** — 아직 깨집니다 |
| **같은 주문에 4,000원 3건 동시** (결제 10,000원) | **3건 모두 202**, 접수 합계 **12,000원** — 아직 깨집니다 |
| **같은 주문 2건, 앞 건이 느림** | 둘이 동시에 나가 **뒤 건이 5.8초 먼저** 결제대행사에서 처리됨 — 아직 깨집니다 |

> 촬영 포인트: 여기서 동시 요청 명령(`xargs -P 5`)을 실행해 **직접 깨뜨려 보이는 것**이 3단계의 동기가 됩니다.
> 깨지는 이유는 코드에 주석으로 표시해 두었습니다 — `RefundService`의 "조회와 저장 사이", "합계와 저장 사이",
> `RefundWorker.tick()`의 "막는 단위가 건(id)이라 같은 주문이 나란히 나가는 자리".

## 3단계 — 락의 범위와 처리 단위 설계 (`../solution/`)

**바꾸는 것은 두 군데뿐입니다.**

| 클래스 | 단위 | 왜 그 단위인가 |
|---|---|---|
| `RefundService` | `orderId` 단위 락 | 중복 확인·한도 합계·저장이 **한 덩어리**로 끝나야 하는 범위가 "한 주문의 환불 목록"이기 때문 |
| `RefundWorker` | `orderId` 단위 처리 | 순서를 지켜야 하는 범위가 "한 주문"이기 때문. 주문 하나를 작업 하나로 맡기고 **가장 오래된 미종결 건만** 보냄 |

여기에 더해 `Refund.refundId`에 **DB 유일 제약**을 걸어, 락이 듣지 않는 상황(서버 여러 대)까지 마지막으로 막습니다.

**바꾼 뒤 같은 명령을 다시 실행하면** (실측)

| 확인 | 2단계 | 3단계 |
|---|---|---|
| 같은 환불 ID로 동시 5건 | 5건 저장, 조회 500 | **1건만 202, 나머지 4건은 200 `duplicate`**, 저장 1건 |
| 같은 주문에 4,000원 3건 동시 | 3건 모두 접수(12,000원) | **202, 202, 422** — 접수 합계 8,000원 |
| 같은 주문 2건, 앞 건이 느림 | 뒤 건이 5.8초 먼저 처리 | 뒤 건은 **앞 건이 끝난 뒤** 전달 (+3초 시점 `attemptCount: 0`) |
| 느린 건이 있을 때 다른 주문 | 0.9초 (영향 없음) | 1.2초 (영향 없음) |

## 세 단계를 각각 실행해 측정한 시나리오 표

| | 시나리오 | 1단계 | 2단계 | 3단계 |
|---|---|---|---|---|
| S1 | 정상 접수 202, 결제대행사를 기다리지 않음 | ○ | ○ | ○ |
| S2 | 같은 ID·같은 내용 → 200 `duplicate` | ✕ | **○** | ○ |
| S3 | 같은 ID·다른 내용 → 409 | ✕ | **○** | ○ |
| S4 | 같은 ID 동시 5건 → 1건만 저장 | ✕ | ✕ | **○** |
| S5 | 한도 초과 → 422 + `REJECTED` 저장 | ✕ | **○** | ○ |
| S6 | 같은 주문 동시 3건 → 합계가 한도를 넘지 않음 | ✕ | ✕ | **○** |
| S7 | 입력 오류 → 400 | ✕ | **○** | ○ |
| S8 | 결제대행사 `SUCCESS` → `COMPLETED` | ○ | ○ | ○ |
| S9 | `FAIL`·5xx → 최대 3회 재시도 후 `FAILED` | ✕ | **○** | ○ |
| S10 | 응답 지연 → 시간 초과로 보고 재시도 | ✕ | **○** | ○ |
| S11 | 같은 주문은 한 건씩, 다른 주문은 동시에 | △ | ✕ | **○** |
| S12 | 지연됐지만 처리된 건 → 환불 1번, `COMPLETED` | △ | ○ | ○ |
| S13 | 주문별 목록 조회(최신순, 페이지) | ✕ | **○** | ○ |
| | 없는 ID 조회 → 404 | ✕ | **○** | ○ |

**△는 통과했지만 맞아서 통과한 것이 아닙니다.**

- **S11**은 1단계에 워커 스레드가 하나뿐이라 모든 주문이 줄을 서서 생긴 결과입니다. 느린 건 하나가 **다른 주문까지 13초** 밀어 버립니다. 2단계에서 스레드 풀을 넣는 순간 같은 주문의 순서가 깨지고(뒤 건이 5.8초 먼저 처리), 3단계에서 주문 단위로 묶어야 비로소 둘 다 만족합니다.
- **S12**는 1단계에 응답 대기 시간이 없어 12초를 끝까지 기다렸기 때문에 이중 환불이 없었던 것입니다. 2단계처럼 5초에 끊고 **같은 `refundId`로** 재시도해도 1번만 처리되어야 진짜 통과입니다.

> 촬영에서 꼭 짚을 지점입니다 — **"일단 돌아간다"와 "요구사항을 만족한다"는 다릅니다.**
> 2단계는 1단계보다 기능이 많아졌지만, S11은 오히려 ○에서 ✕로 바뀝니다. 동시 처리를 넣으면
> 순서를 따로 설계해야 한다는 것이 이 과제의 핵심입니다.

각 단계를 `./gradlew bootRun --args='--server.port=XXXX'`로 띄우고 같은 요청을 보내 측정했습니다.
결제대행사 응답은 가상 결제대행사의 `POST /admin/script`로 고정했습니다(`SUCCESS`, `FAIL`, `ERROR`, `SLOW`=12초 지연 후 실패, `SLOW_BUT_PROCESSED`=12초 지연되지만 실제로는 처리됨).
