# 과제 2. 결제 한도 차감 + 수수료 정책: 평가 기준표

> 튜터용 문서 · **최종본 v1.2** (2026-10-08)
> 튜터가 수강생 제출물을 직접 실행하고 읽어서 채점합니다. 함께 쓰는 자료: 같은 폴더의 `solution/`(정답 서버)

---

## 1. 평가 원칙

1. 모든 항목은 **ID, 판정 질문, 증거 위치, 판정 방법, 수준별 기준**을 가집니다.
2. **실행으로 판정 가능한 것(A)** 은 튜터가 서버를 띄워 요청을 보내 확인하고, **읽고 판단하는 것(B, C, D)** 은 튜터가 코드와 문서를 읽고 판정합니다.
3. 판정은 **증거에 근거**합니다. 파일과 위치, 응답을 적습니다.
4. 애매하면 낮은 수준이 아니라 **"판정 보류"** 로 표시하고 이유를 적습니다.
5. 이 과제의 핵심 능력은 **정확성과 설명**입니다. 그래서 정확성(A)과 스스로 검증(B) 비중이 높고, 설명(C)이 그다음입니다.

## 3. 평가 절차

### 3-1. 사전 확인
| 확인 | 기준 | 실패 시 |
|---|---|---|
| 실행 | `./gradlew bootRun`으로 8080에서 기동 | **A 영역 0점**, B~D는 코드·문서로 진행 |
| 수강생 테스트 | `./gradlew test` 실행 결과 기록 | B4에서 반영 |

### 3-2. 평가 순서
1. `./gradlew test`를 실행해 결과를 기록한다.
2. 서버를 기동하고 4장의 **확인 방법**대로 S1~S12를 실행한다 (수강생 저장소의 `requests.http`와 curl).
3. A 점수를 매긴다.
4. 수강생의 테스트 코드를 읽고 B를, 서술을 읽고 C를, 코드를 읽고 D를 판정한다.
5. **치명 오류**를 확인해 감점을 적용한다.
6. 결과를 9장 양식으로 기록한다.

> **동시 요청 보내기 (A3~A5, A9, A11)**: 셸에서 `for i in $(seq 1 10); do curl -s -X POST ... & done; wait`처럼 `&`로 동시에 보낸 뒤, 응답 코드 개수와 `GET /api/v1/users/{userId}/limit`의 사용액을 확인합니다.
>
> **정답 서버와 비교하기**: 판단이 애매하면 `solution/`을 띄워 같은 요청을 보내 보면 기대 동작을 바로 확인할 수 있습니다.

| 하 | 1 | 컨트롤러에 로직이 몰려 있음 |

(전역 잠금은 **정당한 대안**이므로 정확성(A)에서는 감점하지 않고, 이유가 서술에 있으면 C2에서 인정합니다.)

### D3. 에러 응답과 일관성 (3점)
| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 3 | 에러가 **공통 형식과 코드**로 일관되게 응답됨 (예외 처리기 등) |
| 중 | 2 | 대부분 일관되나 일부 경로가 다름 |
| 하 | 1 | 제각각 |

### D4. 불필요한 변경 (3점)
**판정 질문**: 과제와 관계없는 파일이나 코드를 건드리지 않았는가? (수정 금지 파일은 수강생이 고치지 않았다고 보고 별도 검사는 하지 않습니다. 코드 리뷰 중 눈에 띄는 변경만 봅니다.)

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 3 | 과제와 관계없는 변경이 없음 |
| 중 | 2 | 관계없는 변경이 조금 있음 (불필요한 포맷 변경, 쓰지 않는 코드 등) |
| 하 | 0 | 수정 금지로 안내된 파일을 고친 것이 코드 리뷰 중 눈에 띔 |
