# 서술

## 문제 5. 풀이 이유

### 5-1. 동시성 처리 방식과 이유

같은 결제 ID는 사용자와 무관하게 전역에서 유일해야 하므로(S4), **결제 ID 하나마다 모니터 락**을 두고
"이미 있는지 확인 → 없으면 승인 처리"를 이 락 안에서 통째로 수행했습니다. 락 키가 결제 ID 자체라서
같은 ID를 같은 사용자가 보내든 다른 사용자가 보내든 한 스레드만 통과합니다. 거절(422)로 끝나면
저장을 하지 않고 락을 빠져나가므로, 별도로 "선점 해제" 코드 없이도 그 ID는 자동으로 재사용 가능한
상태로 남습니다.

한도(사용액 읽기 → 판단 → 쓰기)는 **사용자 ID마다** 별도의 락으로 보호했습니다. 서로 다른 사용자의
결제는 완전히 병렬로 처리되고, 같은 사용자의 결제만 직렬화됩니다. 잠금 순서를 항상 "결제 ID 락 →
사용자 락" 한 방향으로 고정해 교착 상태를 피했습니다.

**다른 선택지와 비교**: 전역 `synchronized`로 모든 승인·취소를 직렬화하는 방법도 정확성 면에서는
동일하게 통과합니다. 구현이 훨씬 단순하지만, 서로 다른 사용자의 결제까지 전부 줄을 세우므로
동시 처리량이 크게 떨어집니다. 이번 과제 규모에서는 체감하기 어렵지만, 사용자가 많아질수록
사용자 단위 락과의 격차가 커질 것으로 판단해 사용자 단위 락을 선택했습니다.

### 5-2. 수수료 정책 구현 방식과 이유

규칙 표의 적용 순서(면제 → 수수료율 결정 → 고액 감면 → 절사·최소 → 상한)를 코드에서도 그대로
단계로 나누어, 표의 각 줄과 코드의 각 단계가 1:1로 대응하도록 만들었습니다. 수수료율은 **bp
정수**로만 다루고, 최종 계산도 정수 나눗셈(`amount * bp / 10000`)으로 끝내 소수점 오차나
반올림·절사 혼동이 생기지 않게 했습니다.

**다른 선택지와 비교**: `double`로 계산한 뒤 `Math.floor`를 쓰는 방법도 가능하지만, 부동소수점은
`999,999.9999...`처럼 경계값 근처에서 오차가 생길 수 있습니다(뼈대에 제공된 기존 코드가 실제로
`Math.round`를 쓰다가 절사 규칙을 어기는 함정이 있었습니다). 정수 연산은 애초에 그런 오차가
생길 수 없어서 정수 방식을 선택했습니다.

### 5-3. 테스트 설계와 이유

동시성 테스트는 `CountDownLatch`로 모든 스레드를 "준비" 상태까지 세운 뒤 한 번에 출발시키고,
① 성공/충돌/거절 **개수**와 ② 최종 사용액(불변 조건: 사용액 = 취소되지 않은 승인 결제의 합)을
함께 검증했습니다. 개수만 확인하면 "우연히 개수는 맞았지만 사용액이 틀어진" 경우를 놓칠 수
있기 때문입니다. 수수료 테스트는 규칙이 바뀌는 경계값(999원/1,000원, 999,999원/1,000,000원)과
등급·유형 조합을 표에서 그대로 옮겨 파라미터화 테스트로 정리했습니다.

**다른 선택지와 비교**: `Thread.sleep`으로 타이밍을 맞추는 방법도 고려했지만, 실행 환경에 따라
결과가 흔들릴 수 있어 래치로 정확히 동시 출발을 보장하는 방식을 선택했습니다.

### 5-4. 중요하게 생각한 점

"정확히 몇 건이 성공해야 하는가"와 "최종 상태가 불변 조건을 지키는가"를 항상 같이 확인하는 것을
가장 중요하게 생각했습니다. 동시성 버그는 대부분 평균적으로는 맞아 보이다가 가끔 틀어지므로,
개수만 세는 검증으로는 놓치기 쉽습니다.

## 문제 6. 가장 어려웠던 문제

### 6-1. 문제 상황

처음에는 사용자 단위 락 하나로 모든 동시성 문제(중복 결제 ID, 한도 초과)를 해결하려고 했습니다.
S3(같은 사용자, 같은 결제 ID 동시 요청)까지는 잘 통과했지만, S4(**다른 사용자가 같은 결제 ID**를
동시에 보내는 경우)에서 두 사용자가 서로 다른 락을 잡고 동시에 통과해 같은 결제 ID가 두 번
승인되는 문제가 발견됐습니다.

### 6-2. 원인 파악과 해결 과정

사용자 단위 락은 "같은 사용자"라는 조건에서만 상호 배제를 보장하는데, 결제 ID의 유일성은
"사용자와 무관하게 전체에서" 지켜져야 하는 규칙이라 애초에 범위가 맞지 않았습니다. 이 사실을
S4 시나리오를 재현하는 테스트를 직접 만들어 실행해 보고서야 명확히 알게 됐습니다.
해결책은 락의 기준을 사용자에서 **결제 ID 자체**로 바꾸는 것이었고, 그 위에 한도 계산을 위한
사용자 단위 락을 별도로 하나 더 두었습니다.

### 6-3. 결과와 배운 점

두 종류의 락(결제 ID 락, 사용자 락)을 목적에 맞게 나눈 뒤 S3, S4, S5, S9, S11을 모두 통과했습니다.
"무엇을 지켜야 하는가(불변 조건)"를 먼저 정확히 정의하고, **락의 범위를 그 불변 조건의 범위와
맞추는 것**이 핵심이라는 것을 배웠습니다. 락을 걸었다는 사실보다 "무엇을 기준으로 걸었는가"가
더 중요했습니다.
