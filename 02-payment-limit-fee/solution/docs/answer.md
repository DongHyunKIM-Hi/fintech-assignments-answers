# 서술

## 문제 5. 풀이 이유

### 5-1. 동시성 처리 방식과 이유

결제 ID는 사용자와 관계없이 전체에서 유일해야 합니다(S4). 그래서 결제 ID마다 모니터 락을 두고, 이미 있는 결제인지 확인하는 일부터 승인 처리까지를 이 락 안에서 한 번에 수행했습니다. 락의 기준이 결제 ID이므로 같은 ID를 같은 사용자가 보내든 다른 사용자가 보내든 한 스레드만 통과합니다. 한도 초과(422)로 거절되면 아무것도 저장하지 않고 락을 빠져나가므로, 선점을 해제하는 코드를 따로 두지 않아도 그 ID는 다시 사용할 수 있습니다.

한도 처리(사용액 읽기, 판단, 쓰기)는 사용자 ID마다 별도의 락으로 보호했습니다. 서로 다른 사용자의 결제는 병렬로 처리되고, 같은 사용자의 결제만 차례로 처리됩니다. 락은 항상 결제 ID 락, 사용자 락 순서로 걸어 교착 상태가 생기지 않게 했습니다.

전역 `synchronized`로 모든 승인과 취소를 차례로 처리하는 방법도 정확성 시나리오는 똑같이 통과합니다. 구현은 훨씬 단순하지만, 서로 다른 사용자의 결제까지 모두 줄을 세우기 때문에 동시 처리량이 크게 떨어집니다. 이번 과제 규모에서는 차이를 느끼기 어렵지만 사용자가 많아질수록 사용자 단위 락과의 차이가 커진다고 판단해 사용자 단위 락을 선택했습니다.

### 5-2. 수수료 정책 구현 방식과 이유

규칙 표의 적용 순서(면제, 수수료율 결정, 고액 감면, 버림과 최소 수수료, 최대 수수료)대로 코드도 단계를 나눠서, 표의 각 줄과 코드의 각 단계가 1:1로 대응하게 만들었습니다. 수수료율은 bp 단위 정수로만 다루고, 마지막 계산도 정수 나눗셈(`amount * bp / 10000`)으로 끝내서 소수점 오차나 반올림과 버림을 혼동할 여지를 없앴습니다.

`double`로 계산한 뒤 `Math.floor`를 쓰는 방법도 있지만, 부동소수점은 경계값 근처에서 `999,999.9999...`처럼 오차가 생길 수 있습니다. 실제로 시작 프로젝트의 기존 코드는 `Math.round`를 써서 버림 규칙을 지키지 않았습니다. 정수 연산에서는 이런 오차가 생기지 않기 때문에 정수 방식을 선택했습니다.

### 5-3. 테스트 설계와 이유

동시성 테스트는 `CountDownLatch`로 모든 스레드를 준비시킨 뒤 한 번에 출발시켰습니다. 그리고 성공, 충돌, 거절 응답의 개수와 최종 사용액(사용액 = 취소되지 않은 승인 결제의 합)을 함께 검증했습니다. 개수만 확인하면 개수는 맞았지만 사용액이 틀린 경우를 놓칠 수 있기 때문입니다. 수수료 테스트는 규칙이 바뀌는 경계값(999원과 1,000원, 999,999원과 1,000,000원)과 등급, 결제 유형 조합을 표에서 그대로 옮겨 파라미터화 테스트로 정리했습니다.

`Thread.sleep`으로 타이밍을 맞추는 방법도 고려했지만, 실행 환경에 따라 결과가 달라질 수 있어 래치로 동시 출발을 보장하는 방식을 선택했습니다.

### 5-4. 중요하게 생각한 점

몇 건이 성공해야 하는지와 최종 상태가 불변 조건을 지키는지를 항상 함께 확인했습니다. 동시성 버그는 대부분의 실행에서는 맞아 보이다가 가끔 틀리기 때문에, 개수만 세는 검증으로는 놓치기 쉽습니다.

## 문제 6. 가장 어려웠던 문제

### 6-1. 문제 상황

처음에는 사용자 단위 락 하나로 결제 ID 중복과 한도 초과를 모두 막으려고 했습니다. 같은 사용자가 같은 결제 ID로 동시에 요청하는 S3는 통과했습니다. 하지만 다른 사용자가 같은 결제 ID로 동시에 요청하는 S4에서는 두 사용자가 서로 다른 락을 잡고 동시에 통과해서, 같은 결제 ID가 두 번 승인되었습니다.

### 6-2. 원인 파악과 해결 과정

사용자 단위 락은 같은 사용자의 요청끼리만 서로 막아 줍니다. 그런데 결제 ID의 유일성은 사용자와 관계없이 전체에서 지켜야 하는 규칙이라 락의 범위가 맞지 않았습니다. S4 상황을 재현하는 테스트를 직접 만들어 실행해 보고 나서야 이 점을 알게 되었습니다. 그래서 락의 기준을 사용자에서 결제 ID로 바꾸고, 한도 계산을 위한 사용자 단위 락을 따로 하나 더 두었습니다.

### 6-3. 결과와 배운 점

결제 ID 락과 사용자 락을 목적에 맞게 나눈 뒤 S3, S4, S5, S9, S11을 모두 통과했습니다. 지켜야 할 불변 조건을 먼저 정의하고, 락의 범위를 그 불변 조건의 범위에 맞춰야 한다는 것을 배웠습니다. 락을 걸었는지보다 무엇을 기준으로 걸었는지가 더 중요했습니다.
