# 단계별 구현 — 결제 한도 차감과 수수료 정책

해설 영상에서 **한 번에 완성하지 않고 세 단계로 나눠** 만들어 가기 위한 코드입니다.
각 단계는 그대로 실행되는 프로젝트이고, 다음 단계는 앞 단계에 얹는 구조입니다.

| 단계 | 폴더 | 한 문장 |
|---|---|---|
| 1 | `step1-정상경로/` | 승인·취소·조회 흐름이 도는지만 확인합니다. 수수료는 1.00% 하나, 예외도 락도 없습니다. |
| 2 | `step2-예외처리/` | 입력 검증, 상태 코드(400/409/422/404), 수수료 규칙 10개를 채웁니다. 아직 락은 없습니다. |
| 3 | `../solution/` | 락의 범위를 설계해 동시성을 해결합니다. |

실행은 어느 폴더에서든 같습니다.

```bash
./gradlew bootRun
```

- 촬영 때는 포트를 나눠 띄웠습니다. 1단계 8121, 2단계 8122 (`./gradlew bootRun --args='--server.port=8121'`).
- 수정 금지 파일(`LimitStore`, `PaymentRecord`, `PaymentState`, API 경로와 요청·응답 형식)은 세 단계 모두 그대로입니다.
- 단계 폴더에는 `src/test`가 없습니다. 테스트는 3단계(최종본)에만 있습니다.

## 1단계 — 정상 경로

**만드는 것**: 결제 승인(사용액 차감 + 수수료), 취소, 한도 조회, 수수료 계산. 서비스 클래스로 분리하되 내용은 최소한으로 둡니다.

**일부러 하지 않는 것**: 입력 검증과 에러 응답, 중복·한도·취소 상태 판정, 수수료 규칙(기본 1.00%만), 동시성 제어.

**실행하면 이렇게 됩니다** (실측)

| 확인 | 결과 |
|---|---|
| 정상 승인 (GOLD 국내 50,000원) | 200, `remainingLimit: 950000`, `fee: 500` (규칙 표는 250원) |
| 승인된 결제 취소 → 한도 조회 | 200, 사용액이 결제 금액만큼 줄어듦 |
| 같은 결제 ID로 다시 승인 | **200** (409가 되어야 함 → 2단계), 사용액 두 배 |
| 1,500,000원 승인 | **200**, `remainingLimit: -500000` (422가 되어야 함 → 2단계) |
| `amount` 0 / 음수 / 누락 | **200**, **200**(`fee: -50`), **500** (모두 400이 되어야 함 → 2단계) |
| 없는 결제 취소 | **500** (404가 되어야 함 → 2단계) |
| 같은 결제를 두 번 취소 | **둘 다 200**, 사용액 두 번 감소 (409가 되어야 함 → 2단계) |
| 수수료 계산 예시 8개 | **2개만 일치** (12,350원→123원, 999,999원→9,999원) |
| 같은 결제 ID 10건 동시 | **10건 모두 200** (1건만 200이어야 함 → 3단계) |
| 400,000원 3건 동시 | **3건 모두 200**, 사용액 400,000 (2건 200·1건 422에 사용액 800,000이어야 함 → 3단계) |

> 촬영 포인트: "일단 돌아간다"와 "요구사항을 만족한다"가 다르다는 것을 여기서 보여 줍니다.
> 특히 수수료는 흐름상 아무 문제가 없어 보이지만 표와는 거의 다 틀립니다.

## 2단계 — 예외 처리와 수수료 규칙

**추가하는 것**
- `GlobalExceptionHandler`로 에러 응답 형식(`{"code","message","paymentId"}`)을 통일
- 입력 검증 → 400 `INVALID_REQUEST` (`@Valid`와 제약 애노테이션, 수수료 API 금액 범위, 소수 금액 거절 설정)
- 결제 ID 중복 → 409 `DUPLICATE_PAYMENT`, 한도 초과 → 422 `LIMIT_EXCEEDED`(거절한 결제는 저장하지 않음)
- 취소 → 200 / 404 `PAYMENT_NOT_FOUND` / 409 `ALREADY_CANCELED`
- `FeePolicy`를 규칙 표 전체(R1\~R10)로 채우고 bp 단위 **정수**로 계산

**여전히 하지 않는 것**: 동시성 제어.

**실행하면 이렇게 됩니다** (실측)

| 확인 | 결과 |
|---|---|
| S1 정상 승인 | 200, `fee: 250`, `remainingLimit: 950000` |
| S2 순차 중복 | 409 `DUPLICATE_PAYMENT` |
| S6 한도 경계 (1,000,000 → 1원 → 취소 → 거절됐던 ID 재요청) | 200 → 422 → 200 → 200 |
| S7 입력 오류 5종 (`amount` 0·음수·누락, `grade` 오타, 10.5) | 모두 400, 저장되지 않음 |
| S8 없는 결제 취소 / S9 순차 이중 취소 / S10 취소 후 재승인 | 404 / 409 / 409 |
| S12 수수료 | README 계산 예시 8개, 평가 기준표 A12 확인 벡터 24개 **전부 일치** |
| **S3 같은 결제 ID 10건 동시** | **10건 모두 200** — 아직 깨집니다 (사용액 100,000) |
| **S4 다른 사용자 10명이 같은 ID로 동시** | **10건 모두 200** — 아직 깨집니다 |
| **S5 400,000원 3건 동시** | **3건 모두 200**, 사용액 400,000. 이어서 600,000원도 승인되어 **승인 합계 1,800,000** |
| **S9 같은 결제 취소 10건 동시** | **10건 모두 200**, 사용액 **-300,000** (5회 중 3회) |
| **S11 취소와 승인 동시(900,000 취소 + 100,000 승인)** | 둘 다 200인데 **사용액 1,000,000** (취소되지 않은 승인은 100,000뿐) |

> 촬영 포인트: 여기서 동시 요청 명령을 실행해 **직접 깨뜨려 보이는 것**이 3단계의 동기가 됩니다.
> 사용액이 음수가 되는 동시 취소(`-300,000`)와 승인 합계가 한도를 넘는 S5가 가장 잘 보입니다.
> 깨지는 이유는 `PaymentService`에 주석으로 표시해 두었습니다 — "중복 확인과 저장 사이", "읽기·판단·쓰기 사이".
>
> 주의: 사용액은 덮어쓰기라서 동시 요청이 실패해도 숫자가 우연히 맞아 보일 때가 있습니다(S5의 800,000, S9의 0).
> 그래서 **응답 코드 개수와 사용액을 함께** 봐야 합니다. 평가 기준표 B2가 둘 다 검증하라고 요구하는 이유이기도 합니다.

## 3단계 — 락의 범위 설계 (`../solution/`)

**바뀌는 파일은 `PaymentService` 하나뿐입니다.** 수수료(`FeePolicy`)와 예외 처리는 2단계 그대로입니다.

| 락 | 키 | 왜 그 키인가 |
|---|---|---|
| 결제 ID 락 | `paymentId` | 중복되면 안 되는 단위가 "결제 ID 하나"이기 때문. 사용자와 무관한 키라서 **다른 사용자가 같은 ID**를 보내도(S4) 막힙니다 |
| 사용자 락 | `userId` | 한도를 지켜야 하는 단위가 "한 사용자의 사용액"이기 때문. 다른 사용자의 결제는 그대로 병렬 처리됩니다 |

핵심은 **판단과 변경을 같은 락 안에 묶는 것**입니다.
- 승인: 기존 결제 **확인 + 사용액 읽기 + 한도 판단 + 쓰기 + 기록 저장**을 한 덩어리로
- 취소: 취소 상태 **확인 + 사용액 복원 + 기록 저장**을 한 덩어리로

여기에 더해 두 가지가 따라옵니다.
- 락은 항상 **결제 ID 락 → 사용자 락** 순서로 겁니다. 순서를 섞으면 교착 상태가 생깁니다.
- 한도 초과로 거절할 때는 아무것도 저장하지 않고 락을 빠져나갑니다. 그래서 **선점을 해제하는 코드 없이** 거절된 ID를 다시 쓸 수 있습니다(S6).

> 촬영 포인트: 전역 락 하나(`synchronized` 메서드)로도 시나리오는 모두 통과합니다.
> 다만 `LimitStore` 호출마다 50\~150ms가 걸리므로, 서로 다른 사용자의 결제까지 줄을 세우면 느려집니다.
> 평가에서 락의 범위를 보는 이유입니다(평가 기준표 D2). 2단계로 되돌려 같은 명령을 다시 실행하면 차이가 바로 보입니다.
