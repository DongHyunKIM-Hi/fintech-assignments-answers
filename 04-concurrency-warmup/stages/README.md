# 단계별 구현 — 쿠폰 사용과 회의실 예약

해설 영상에서 **한 번에 완성하지 않고 세 단계로 나눠** 만들어 가기 위한 코드입니다.
각 단계는 그대로 실행되는 프로젝트이고, 다음 단계는 앞 단계에 얹는 구조입니다.

| 단계 | 폴더 | 한 문장 |
|---|---|---|
| 1 | `step1-정상경로/` | 설계한 흐름이 도는지만 확인합니다. 예외도 락도 없습니다. |
| 2 | `step2-예외처리/` | 입력 검증과 에러 응답을 채웁니다. 아직 락은 없습니다. |
| 3 | `../solution/` | 락의 범위를 설계해 동시성을 해결합니다. |

실행은 어느 폴더에서든 같습니다.

```bash
./gradlew bootRun
```

---

## 1단계 — 정상 경로

**만드는 것**: 쿠폰 발급·조회·사용, 예약 생성·조회. 서비스 클래스로 분리하되 내용은 최소한으로 둡니다.

**일부러 하지 않는 것**: 입력 검증, 에러 응답, 동시성 제어.

**실행하면 이렇게 됩니다** (실측)

| 확인 | 결과 |
|---|---|
| 쿠폰 발급 → 사용 | 204 → 200, 할인액이 가장 큰 쿠폰이 선택됨 |
| 정상 예약 | 201 |
| 쿠폰이 없는데 사용 | **500** (404가 되어야 함 → 2단계) |
| 겹치는 시간에 예약 | **201** (409가 되어야 함 → 2단계) |
| 쿠폰 1장에 동시 5건 | **전부 200** (1건만 200이어야 함 → 3단계) |

> 촬영 포인트: "일단 돌아간다"와 "요구사항을 만족한다"가 다르다는 것을 여기서 보여 줍니다.

---

## 2단계 — 예외 처리와 시나리오

**추가하는 것**
- `GlobalExceptionHandler`로 에러 응답 형식(`{"code","message"}`)을 통일
- 쿠폰: 보유 쿠폰 없음 → 404 `NO_COUPON_AVAILABLE`, `amount` 0 이하 → 400, 잘못된 `type` → 400
- 예약: 시간 형식과 `from >= to` 검증 → 400, 겹침 판정 → 409 `TIME_CONFLICT`, 끝과 시작이 맞닿은 것은 겹치지 않음

**여전히 하지 않는 것**: 동시성 제어.

**실행하면 이렇게 됩니다** (실측)

| 확인 | 결과 |
|---|---|
| 쿠폰 없음 | 404 |
| `amount` 0 / 잘못된 `type` | 400 |
| 차례로 겹치는 예약 | 409 |
| 끝과 시작만 맞닿음 | 201 |
| `from >= to`, `25:00` | 400 |
| **쿠폰 1장에 동시 5건** | **전부 200** — 아직 깨집니다 |
| **같은 회의실 동시 5건** | **여러 건 201** — 아직 깨집니다 |

> 촬영 포인트: 여기서 동시 요청 명령을 실행해 **직접 깨뜨려 보이는 것**이 3단계의 동기가 됩니다.
> 깨지는 이유는 코드에 주석으로 표시해 두었습니다 — "찾기와 삭제 사이", "겹침 확인과 저장 사이".

---

## 3단계 — 락의 범위 설계 (`../solution/`)

**바꾸는 것은 두 군데뿐입니다.**

| 서비스 | 락 키 | 왜 그 키인가 |
|---|---|---|
| `CouponService` | `userId` | 중복되면 안 되는 단위가 "한 사용자의 쿠폰 목록"이기 때문 |
| `ReservationService` | `roomId` | 겹침을 판단하는 범위가 "한 회의실의 예약 목록"이기 때문 |

핵심은 **판단과 변경을 같은 락 안에 묶는 것**입니다.
- 쿠폰: 가장 큰 할인 쿠폰 **찾기 + 삭제**를 한 덩어리로
- 예약: 겹침 **확인 + 저장**을 한 덩어리로

여기에 더해 `CouponStore`가 내부 리스트를 그대로 돌려주므로, 락 안에서 **복사본**을 떠서 훑습니다.

> 촬영 포인트: 전역 락 하나(`synchronized` 메서드)로도 시나리오는 통과하지만,
> 다른 사용자·다른 회의실 요청까지 줄을 세우게 됩니다. 평가에서 락의 범위를 보는 이유입니다.
> 2단계로 되돌려 같은 명령을 다시 실행하면 차이가 바로 보입니다.

---

## 세 단계를 각각 실행해 측정한 시나리오 표

| | 시나리오 | 1단계 | 2단계 | 3단계 |
|---|---|---|---|---|
| S1 | 쿠폰 발급 후 사용 — 가장 큰 할인 적용 | ○ | ○ | ○ |
| S2 | 쿠폰 2장, 동시 2건 → 둘 다 성공 | ✕ | ✕ | **○** |
| S3 | 쿠폰 1장, 동시 5건 → 1건만 성공 | ✕ | ✕ | **○** |
| S4 | 쿠폰 없을 때 404 | ✕ | **○** | ○ |
| S5 | 다른 사용자 동시 사용 → 둘 다 성공 | △ | △ | ○ |
| S6 | 정상 예약 201 | ○ | ○ | ○ |
| S7 | 차례로 겹치는 예약 409 | ✕ | **○** | ○ |
| S8 | 같은 회의실 동시 5건 → 1건만 201 | ✕ | ✕ | **○** |
| S9 | 끝과 시작만 맞닿음 → 둘 다 201 | △ | ○ | ○ |
| S10 | 다른 회의실 동시 → 둘 다 201 | △ | △ | ○ |
| S11 | 사용자별 예약 조회 | ○ | ○ | ○ |
| | 입력 검증 400 (4종) | ✕ | **○** | ○ |

**△는 통과했지만 맞아서 통과한 것이 아닙니다.**

- **S9**는 1단계에 겹침 검사 자체가 없어서 둘 다 201이 나온 것입니다. 2단계에서 검사를 넣고도 201이어야 진짜 통과입니다.
- **S5·S10**은 1·2단계에 락이 없어서 서로 기다리지 않은 것입니다. 3단계에서 락을 넣고도 기다리지 않아야 의미가 있습니다.

> 촬영에서 꼭 짚을 지점입니다 — **"테스트가 초록색"과 "요구사항을 만족한다"는 다릅니다.**

각 단계를 `./gradlew bootRun --args='--server.port=XXXX'`로 띄우고 같은 요청을 보내 측정했습니다 (동시성 항목은 3회씩 반복).
