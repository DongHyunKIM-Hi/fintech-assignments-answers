# 과제 4. 쿠폰 사용과 회의실 예약 평가 기준표

> 평가자용 문서, v1.5 (2026-11-16)
> - 워밍업 과제라 기준표도 짧습니다.
> - 평가자가 지원자 제출물을 직접 실행하고, 코드와 문서를 읽어 채점합니다.
> - 같은 폴더의 `solution/`(정답 서버)을 함께 사용합니다.

---

## 1. 배점 요약

| 영역 | 배점 | 판정 방법 |
|---|---|---|
| A. 정확성 | 70 | 평가자가 curl이나 IntelliJ HTTP Client로 아래 시나리오를 직접 실행 |
| B. 코드 품질 | 30 | 코드와 README를 읽고 판정 |
| **합계** | **100** | |

### 평가 순서

1. 지원자 서버를 `./gradlew bootRun`으로 8080 포트에서 실행합니다.
2. 2장의 시나리오를 실행합니다. 과제 저장소의 `requests.http`에 순차 요청 예시와 동시 요청용 셸 스크립트 예시가 있습니다.
3. 코드와 README를 읽고 3장의 B 영역을 판정합니다.
4. 4장의 치명 오류가 있는지 확인합니다.

> **동시 요청 보내는 방법 (A2~A4, A7, A9)**
> - 셸에서 `for i in $(seq 1 5); do curl -s -X POST ... & done; wait`처럼 `&`를 붙여 요청을 동시에 보냅니다.
> - **예약 시나리오(A5~A9)를 다시 실행할 때는 회의실 이름을 바꾸거나 서버를 재시작합니다.** 예약은 메모리에 남아, 같은 회의실·같은 시간으로 두 번째 실행하면 전부 409가 됩니다. 과제 저장소 `requests.http`의 **S8·S10 셸 명령**에는 회의실 이름에 `$RANDOM`이 붙어 있어 그대로 다시 쓸 수 있습니다. 그 밖의 예약 요청(A5 정상 예약, A6 순차 겹침, A8 맞닿은 시간)은 회의실 이름이 고정이므로 **다시 실행할 때 회의실 이름을 바꾸거나 서버를 재시작하세요.**
> - 응답 코드별 개수와 조회 결과를 확인합니다.
>
> **정답 서버와 비교하는 방법**
> - 판정이 애매하면 `solution/`을 **다른 포트로** 띄워(`./gradlew bootRun --args='--server.port=8081'`) 같은 요청을 보내 기대 동작을 확인합니다. **지원자 서버를 내리면 안 됩니다** — 메모리 저장이라 쌓은 예약과 쿠폰이 사라집니다.

## 2. 영역 A. 정확성 (70점)

### A-1. 쿠폰 (35점)

| ID (지원자 README 시나리오) | 시나리오 | 배점 | 통과 기준 |
|---|---|---|---|
| A1 (S1) | 정상 사용 | 5 | 보유 쿠폰 중 할인액이 가장 큰 쿠폰이 적용되고 삭제됨 |
| A2 (S2) | 쿠폰 2장 보유, 동시 사용 요청 2건 | 10 | **2건 모두 200**, 서로 다른 쿠폰이 한 장씩 사용됨, 이후 조회하면 쿠폰 0장 |
| A3 (S3) | 쿠폰 1장 보유, 동시 사용 요청 5건 | 15 | **1건만 200**, 나머지 4건은 404. 200이 2건 이상이면 이 항목은 0점이고 치명 오류 F1에 해당 |
| A4 (S5) | 서로 다른 사용자의 동시 사용 | 5 | 두 사용자 모두 각자 올바른 결과를 받음. 전역 락 때문에 서로 기다리더라도 결과가 맞으면 통과이고, 락 범위는 B1에서 판정 |

### A-2. 회의실 예약 (35점)

| ID (지원자 README 시나리오) | 시나리오 | 배점 | 통과 기준 |
|---|---|---|---|
| A5 (S6) | 정상 예약 | 5 | 201 |
| A6 (S7) | 순차 요청에서 시간 겹침 | 5 | 두 번째 요청이 409 |
| A7 (S8) | 같은 회의실, 겹치는 시간 동시 요청 5건 | 15 | **1건만 201**, 나머지는 409. 201이 2건 이상이면 이 항목은 0점이고 치명 오류 F2에 해당. 5건은 **서로 전부 겹치는 시간**(예: 5건 모두 같은 시간)으로 보냅니다. 지원자 저장소 `requests.http`의 S8 명령을 그대로 쓰면 됩니다. 일부만 겹치게 보내면 2건 이상 성공이 정답일 수 있으므로 쓰지 않습니다. |
| A8 (S9) | 같은 회의실, 끝과 시작만 맞닿은 시간 (예: 10시\~11시, 11시\~12시) | 5 | 둘 다 201 |
| A9 (S10) | 다른 회의실, 같은 시간 동시 예약 | 5 | 둘 다 201. 한쪽이 409 등으로 **거절되면** 감점합니다(회의실을 구분하지 않고 겹침을 확인한 경우). 전역 락 때문에 차례로 처리되어 느려지더라도 결과가 맞으면 통과이고, 락 범위는 B1에서 판정합니다. |

- S11(사용자별 예약 조회)은 배점에 넣지 않습니다. 지원자 README에도 같은 내용을 안내했습니다.
- S4(쿠폰이 없을 때 404)는 A3에서 함께 확인되므로 별도 배점을 두지 않습니다.
- 입력 오류(400 `INVALID_REQUEST`)도 배점에 넣지 않습니다. 400을 500으로 응답하더라도 A 영역에서는 감점하지 않습니다(피드백에만 적습니다).

## 3. 영역 B. 코드 품질 (30점)

### B1. 락의 범위 (12점)

- **판정 질문**: 쿠폰은 사용자 단위, 예약은 회의실 단위로 좁게 잠갔는가?

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 12 | 쿠폰은 `userId`, 예약은 `roomId`를 키로 잠금. 다른 사용자나 다른 회의실의 요청은 서로 기다리지 않음 |
| 중 | 6 | 한쪽만 좁게 잠갔거나, 전역 락 하나로 모두 처리함 (결과는 맞지만 범위가 넓음) |
| 하 | 2 | 요청마다 새 락 객체를 만들거나, 락 맵을 `HashMap`으로 두어 동시 접근에서 깨질 수 있음 |
| 없음 | 0 | 락이 없음 |

### B2. 컨트롤러와 로직의 분리 (8점)

- **판정 질문**: 동시성 처리 코드가 서비스 계층에 모여 있는가?

| 수준 | 점수 | 기준 |
|---|---|---|
| 상 | 8 | 별도 서비스 클래스에 **락과 쓰기 로직**(발급·사용·예약 생성)이 모여 있고, 컨트롤러는 그것을 호출함. 단순 조회의 응답 매핑이 컨트롤러에 남아 있는 것은 감점하지 않습니다(정답 코드도 그렇습니다) |
| 중 | 4 | 분리했지만 컨트롤러에 락이나 분기가 일부 남아 있음 |
| 하 | 1 | 컨트롤러에만 모든 로직이 있음 |
| 없음 | 0 | 해당 기능이 구현되지 않아 판정할 코드가 없음 |

## 5. 인정하는 다른 풀이

- 전역 락 하나로 쿠폰과 예약 요청을 모두 차례로 처리해도 정확성(A)은 만점을 받을 수 있습니다.
- 다만 B1(락의 범위)에서는 감점합니다. 락 범위를 판단하는 능력이 이 과제에서 가장 중요한 학습 목표이기 때문입니다.

## 6. 평가 결과 기록 양식

- 모든 평가자가 같은 형식으로 기록합니다.

```json
{
  "applicantId": "A-001",
  "evaluator": "평가자 이름",
  "scores": {
    "A": { "A1": 5, "A2": 10, "A3": 15, "A4": 5, "A5": 5, "A6": 5, "A7": 15, "A8": 5, "A9": 5 },
    "B": { "B1": {"level": "상", "score": 12, "evidence": "CouponService.java:28-40", "reason": "..."},
           "B2": {}, "B3": {}, "B4": {} }
  },
  "fatal": [],
  "hold": [ { "item": "B1", "reason": "판정 보류 사유" } ],
  "total": 82
}
```

- `fatal`에 항목을 넣었다면 **그 치명 오류가 0으로 만드는 영역의 점수를 실제로 0으로 적고** `total`도 그렇게 계산합니다. 예를 들어 `F1`이 있으면 `A1`~`A4`가 모두 0이어야 합니다.

- 판정이 애매하면 낮은 수준을 주지 말고 `hold`에 이유와 함께 남깁니다.
